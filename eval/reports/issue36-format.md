# get_details 응답 형식 평가 (이슈 #36)

생성: `uv run python eval/agent_format_eval.py --report`. before는 근거 발췌·분류·기술·태그를 상세에 넣은 서버, after는 뺀 서버.

| 지표 | before | after |
| --- | --- | --- |
| 실행 (오류 제외) | 96 | 96 |
| ① 열지 않고 인용한 글 | 24/265 (9%) | 17/259 (7%) |
| ② 결과에 없는 블로그 링크 | 0 | 0 |
| ③ 서술 판정 수 | 981 | 940 |
| ③ 근거 없음 | 5/981 (1%) | 15/940 (2%) |

| ⑤ search 호출 (실행당 평균) | 2.40 | 2.41 |
| ⑤ get_details 호출 (실행당 평균) | 0.79 | 0.83 |
| ⑤ sonbae 결과 글자 (실행 중앙값) | 12,420 | 9,338 |

④ 답변 품질 (after 기준, 쌍 96): 승 42 · 무 30 · 패 24

## 해석

M7 과제 32개(design·open·absent·noise·few) × 3회 × 2버전, Claude Code(Sonnet) 헤드리스, 두 버전 모두 의미 검색(Voyage). 검색 462회(리랭커 약 10.0M 토큰), 판정 gpt-5.5 medium $31.5. 서버 연결이 늦어 도구를 쓰지 못한 실행 1건(t01 after r3)은 다시 돌렸다.

### 통과 기준 (실행 전에 정함)

| 지표 | 기준 | 결과 | 판정 |
| --- | --- | --- | --- |
| ① 열지 않고 인용 | after가 5%p 넘게 늘지 않음 | 9% → 7% | 통과 |

### ③ 근거 없음 판정 내용

after 15건을 직접 보면 지어낸 수치·방법은 없었다.

- 부재 주장 6건: "올리브영 글에는 재개 기능이 없다", "구매 vs 구축 비교는 아니다"처럼 글에 없는 것을 말한 서술. 판정기는 요약·발췌만 보므로 부재를 확인할 수 없어 근거 없음으로 봤다. before에도 2건
- 사례에 덧붙인 해석 6건: "사내 BI라 권한 모델이 단순할 수 있다", "위 사례는 모두 읽기 위주 데이터"처럼 에이전트의 추론을 사례에 붙인 서술
- 판정 데이터 누락 1건(o09): 카드의 `기술:` 줄에 있는 기술명을 판정 데이터에 넣지 않아 근거 없음으로 봤다. before의 t24(Netty)도 같은 경우
- 사실과 어긋남 2건(t08 r3, t14 r1): 다른 사례가 있는데 "한 글 외에는 확인하지 못했다"고 하거나, 사례에 없는 세부(Prometheus 호환 인터페이스 유지)를 붙인 서술

근거 발췌를 빼서 원문 세부를 추측으로 채운 경우(지어낸 수치·구현 방법)는 보이지 않았다.

### ④ 답변 품질

기준별(after 승 · 무 · 패): 정확성 18·64·14, 실무 고려 39·36·21, 판단 근거 27·54·15, 상황 적합성 18·69·9, 전달 10·83·3. 분류별 overall: design 16·16·13, open 14·10·6, absent 7·3·2, noise 4·1·1, few 1·0·2. 승패만 놓고 본 부호 검정 p = 0.036. 답변 길이 중앙값은 2,985자 → 2,939자로 비슷하다.

after가 나빠지지 않았다는 데는 충분하지만, 응답 형식 변경이 답변을 낫게 만든 이유는 확인하지 않았다. 같은 조건을 다시 돌렸을 때의 변동 폭을 재지 않았으므로 "개선"으로 결론 내리지 않는다.

### ⑤ 컨텍스트

실행마다 sonbae 결과 글자 수 중앙값이 12,420자 → 9,338자(−25%)다. get_details 호출 수는 실행당 0.79 → 0.83회로 거의 같아, 상세를 더 자주 열어 줄어든 양을 되먹지 않았다. 응답 크기만 재면(eval/response_size.py, 상위 5건) get_details 중앙값이 9,452자 → 4,285자(−54.7%)다.
