# M7. 에이전트 A/B 평가 (확장)

> 상태: **완료** · 직무 근거: AI · 허브: [docs/README.md](../README.md)

동작하는 서버만 있으면 되므로 확장 마일스톤 중 가장 먼저 한다.

## 작업

- 실제 개발 과제 20~30개를 네 조건(`mcp`: 서버 있음, `none`: 서버·웹 없음, `web`: 웹 검색만, `web-ask`: 웹 검색 + 쓰라는 지시)으로 에이전트에게 풀게 하고 답변을 채점 ([기획.md](../기획.md#에이전트-평가-m7))
- 지표: 같은 과제의 두 답변을 비교해 질문한 개발자에게 더 도움이 되는 쪽을 판정 (처음 후보였던 사례 인용률 등은 MCP에 유리해 핵심 지표에서 뺐다, [기획.md](../기획.md#에이전트-평가-m7)). 도구 호출률 등은 진단 지표
- 실행 자동화: Claude Code 헤드리스 모드(`claude -p --output-format stream-json`)로 도구 호출·결과·답변을 기록하고, 시나리오당 여러 번 돌려 비율로 봄

## 완료 기준

네 조건(서버 있음, 없음, 웹 검색, 웹 검색 지시)의 차이를 수치로 기록

## M1에서 넘어온 항목

- **시나리오 재사용**: [M1 실사용 테스트 시나리오](M1.md#실사용-테스트-시나리오)를 출발점으로 쓴다. 호출해야 하는 경우(설계), 호출하지 말아야 하는 경우(CRUD·버그 수정·개념 질문), DB에 없는 주제를 모두 포함
- **채점 방식**: 호출 여부·연 ID·원문 링크는 코드로, 지어낸 내용·사례와 제안의 구분·"없다"고 말했는지는 LLM 채점으로. M1에서 수동으로 한 "같은 인자로 도구를 다시 실행해 답변 속 사실을 대조"를 자동화
- **해석 왜곡**: 인용 수치는 맞지만 근거 문장의 뜻이 바뀐 인용(시나리오 9의 "100ms", "별도 과제로 남겨뒀다")은 서버가 막을 수 없어 채점 항목으로 측정
- **1회 비교의 한계**: 사례 활용 원칙 반영 전후 비교(시나리오 1)는 1회씩이라 효과를 단정하지 못함 → 여러 번 실행해 비율로 확인
- **주의점**: 헤드리스 모드가 MCP 서버 연결을 기다리는지 확인. 사용자 전역 설정(`~/.claude/CLAUDE.md`)이 결과에 영향을 줄 수 있음

## M6에서 넘어온 항목

근거는 [M6 진행 기록](M6.md#진행-기록)의 "실사용에서 드러난 검색 잡음".

- **"대기열" 형태소 분리**: Kiwi가 "대기열"을 `대기` + `열`로 잘라 색인에 "대기열" 토큰이 없다. "열"은 뜻이 여러 가지인 흔한 조각이라 주제 단어가 힘을 잃고, "대기"만 맞은 무관한 글(셀프계산대 대기, 출고 대기)이 관련도 기준을 넘는다. 재현: `search("이벤트 대기열", problem_type="트래픽 급증 대응")`. 사용자 사전에 넣으면 색인 재빌드·`SCHEMA_VERSION` 변경·E9 재평가·새 DB Release가 필요하다. 실제 호출 기록에서 같은 유형(흔한 조각으로 잘리는 주제 단어)을 모아 한 번에 처리한다
- **무관 카드 측정**: Claude Code 실사용(설계 질문)에서 `search` 결과 카드의 상당수가 무관했지만 에이전트가 걸러 인용하지는 않았다. 무관 카드는 맥락을 차지하고 덜 꼼꼼한 에이전트에서는 잘못된 인용 위험이 된다. 호출 기록으로 결과 카드의 무관 비율을 지표에 넣는다
- **"캐시"와 "캐싱"**: 문제 유형 이름은 "캐싱"인데 검색어는 보통 "캐시"라 필터 중복 제외가 적용되지 않는다. `search("캐시 일관성", problem_type="캐싱")`이 48건 통과하고 무관한 글이 섞인다. 같은 뜻의 다른 표기가 관련도에 주는 영향을 함께 본다

## M5에서 넘어온 항목

- **질의 재작성 확인**: M5는 `search` 설명에 "한 주제의 짧은 명사구로, 여러 하위 주제는 나눠 검색"하라고 안내했다. 효과(E9: Recall@5 0.589 → 0.627)는 작은 모델로 흉내 낸 값이라, 실제 에이전트가 검색어를 나누는지, 없는 주제에서 짧은 검색어로 엉뚱한 결과를 소개하지 않는지 측정한다

## 진행 기록

### 1단계: 헤드리스 실행 확인 (2026-10-06)

Claude Code 2.1.286, 저장소 밖 빈 폴더에서 `claude -p --output-format stream-json --verbose`로 확인했다. 모델은 `sonnet`(claude-sonnet-5-5).

| 확인 항목 | 결과 |
| --- | --- |
| MCP 연결 대기 | 기다린다. `system/init` 이벤트의 `mcp_servers`가 이미 `connected`이고, 첫 턴부터 도구를 쓴다. M1 시나리오 6처럼 연결 전에 입력되는 문제는 헤드리스에서는 생기지 않는다 |
| 서버 지정 | `--strict-mcp-config --mcp-config <json>`으로 사용자 MCP(playwright 등)를 빼고 techblog만 붙인다. B 조건은 빈 `mcpServers`를 준다 |
| 기록 추출 | `assistant`의 `tool_use`(이름·인자), `user`의 `tool_result`(결과 텍스트·오류), `result`(최종 답변, `num_turns`, `total_cost_usd`, `duration_ms`, `permission_denials`)로 채점에 필요한 정보를 모두 얻는다 |
| 권한 | `--permission-mode dontAsk --allowedTools "mcp__techblog__search mcp__techblog__get_details mcp__techblog__aggregate"`로 MCP 도구만 허용한다. 나머지 도구 호출은 자동 거부되어 `permission_denials`에 남는다 |
| 사용자 설정·플러그인 | `--setting-sources project`면 사용자 settings와 플러그인(figma 등)이 빠진다 |
| 자동 메모리 | 기본으로 켜져 있어 반복 실행끼리 오염될 수 있다. `--settings '{"autoMemoryEnabled":false}'`로 끈다(`init`의 `memory_paths`가 `None`). 세션 기록은 `--no-session-persistence`로 남기지 않는다 |
| 전역 CLAUDE.md | **위 옵션으로는 빠지지 않는다.** `~/.claude/CLAUDE.md`(응답 언어 규칙만 있음)가 그대로 로드된다. `--safe-mode`는 CLAUDE.md를 빼지만 `--mcp-config` 서버까지 꺼서 A 조건에 못 쓴다. `--bare`(또는 `CLAUDE_CODE_SIMPLE=1`)는 CLAUDE.md를 빼지만 OAuth를 읽지 않아 `ANTHROPIC_API_KEY`가 필요하다 |
| 시간·비용 | 설계 질문 1회에 약 55초, 비용 표시 약 $0.10(A), $0.07(B) |

시험 실행에서 본 것:

- **A (선착순 쿠폰, M1 시나리오 1)**: `search` 2회(검색어 "선착순 쿠폰 발급 동시성 대량 트래픽", "Redis 재고 차감 선착순 이벤트 Kafka") → `get_details` 2건 → 사례와 제안을 나눠 답했다. 다만 `get_details`로 열지 않은 사례(토스 포인트 지급, 올리브영 홈 아키텍처)도 카드만 보고 인용했다. 도구 설명의 "소개할 사례는 모두 열어 확인" 원칙을 어긴 것이라 채점 항목(열지 않은 사례 인용)으로 잰다. MCP 도구는 ToolSearch 없이 바로 호출했다
- **B (MCP 없음)**: 국내 사례를 찾으려고 WebSearch를 2회 시도했다가 거부되자, "기억만으로 쓰면 틀릴 수 있어 사례를 쓰지 않았다"고 밝히고 일반 설계로 답했다. 이를 보고 웹 검색을 허용한 조건을 따로 두기로 했다(`web`, [기획.md](../기획.md#에이전트-평가-m7))

1단계 후 결정 (사용자 결정, [기획.md](../기획.md#에이전트-평가-m7)):

- 조건은 `mcp`·`none`·`web` 세 개. 웹 차단은 `dontAsk` 모드에서 WebSearch·WebFetch를 허용 목록에 넣지 않는 방식으로 하고, 거부된 시도 횟수도 지표로 남긴다
- 전역 CLAUDE.md는 그대로 두고 조건으로 명시한다
- `web` 조건 확인: `--allowedTools "WebSearch WebFetch"`로 헤드리스에서 웹 검색이 동작한다(ToolSearch로 불러온 뒤 호출). 다만 선착순 쿠폰 설계 질문을 그대로 넣었을 때는 웹 검색을 한 번도 하지 않고 1턴에 답했다. 웹 검색을 언제 스스로 쓰는지도 `web` 조건에서 함께 보이는 지표다

### 3단계: 실행기 (2026-10-06)

[eval/agent_run.py](../../eval/agent_run.py). 모델 `sonnet`, 조건별 3회, 호출 금지 과제는 `mcp`만 돌린다(사용자 결정, [기획.md](../기획.md#에이전트-평가-m7)). 과제 28개 기준 234회.

- **출력**: `eval/runs/agent/<name>/raw/`에 stream-json 원본(git 제외), `records.jsonl`에 실행마다 도구 호출(이름·인자·결과)·거부된 도구·답변·턴 수·비용, `meta.json`에 Claude Code 버전·커밋·DB 체크섬
- **격리**: 실행마다 새 임시 폴더에서 돌린다. MCP 서버는 저장소 DB(`TECHBLOG_MCP_DB`)로 고정한다. 원본 로그에 `result` 이벤트가 있는 실행은 건너뛰어 중단 후 이어 돌릴 수 있다
- **물려받은 환경 변수 제거**: Claude Code 세션(데스크톱 앱) 안에서 실행하면 `MCP_CONNECTION_NONBLOCKING`, `CLAUDE_EFFORT` 등 30여 개 변수가 자식 프로세스로 넘어간다. `CLAUDE*`·`ANTHROPIC*`·`MCP_*`를 빼도 저장된 OAuth 로그인은 유지되어, 일반 터미널과 같은 조건으로 돌린다. 실제로 동작이 달랐다. 앱 세션 환경(1단계 시험)에서는 MCP 도구를 바로 호출했지만, 변수를 뺀 환경에서는 ToolSearch로 불러온 뒤 호출했다
- **시험 실행**(t01·t25 1회씩): 4회 모두 정상. t01 `mcp`에서 에이전트가 M6 잡음 재현 검색어인 `search("이벤트 대기열", problem_type="트래픽 급증 대응")`를 스스로 만들었다

### 전체 실행 (2026-10-06)

`mcp`·`none`·`web` 234회(`eval/runs/agent/m7-sonnet/`). 오류 0, `mcp` 조건은 모두 서버 연결 상태로 시작. 비용 표시 합계 $17.6, 실행 시간 합계 약 3시간(4개 동시).

| `mcp` 분류 | 도구 호출 | `get_details`까지 |
| --- | --- | --- |
| 설계 | 45/45 | 45/45 |
| 사례 적음 | 3/3 | 2/3 |
| 검색 잡음 | 6/6 | 6/6 |
| 집계 | 6/6 (모두 `aggregate`) | 6/6 |
| 없는 주제 | 12/12 | 9/12 |
| 호출 금지 | 0/9 | 0/9 |
| 개념 | 0/3 | 0/3 |

- 호출 판단은 기대와 모두 맞았다. 없는 주제에서 상세를 연 9회는 일부 관련 카드를 사례처럼 소개했는지 채점에서 본다
- 호출 금지 과제 t26(Spring Boot CRUD)에서 파일 쓰기(Write) 시도 28회가 권한 모드에서 거부됐다. 검색 도구와는 무관하고 답변은 코드 텍스트로 나왔다
- **`web` 조건은 웹 검색 0회(65회 중).** 도구 목록에 있고 거부도 없었다. 환경 변수 유무·사례 요청 문구·허용 목록 유무를 바꾼 추가 실험 10회도 0회였다(1단계 시험의 시도 1회는 드문 경우). 기억으로 답하며 "기억에 의존한 내용"이라 단서를 달고 웹 검색을 제안했다. 출처 없이 회사를 지목하는 서술("토스: SLASH 발표에서 대기열과 Redis 활용")이 섞여 지어낸 사례 지표에서 센다 → `web-ask` 조건 추가 (사용자 결정, [기획.md](../기획.md#에이전트-평가-m7))
- **네트워크**: 응답 스트림이 끊겨 Claude Code가 다시 받은 실행 4회, API 재시도 5회(모두 t10), 120초를 넘긴 실행 10회(t22~t24에 몰림, 최대 843초, 중앙값 28초). 끊긴 실행도 최종 답변과 도구 기록은 온전했다. 특정 시간대의 일시적 불안정으로 보이며, 소요 시간은 중앙값으로 비교한다
- **`web-ask` 시험**(t01 1회): 웹 검색 2회 + 원문 가져오기 2회 후 올리브영 글을 정확히 인용했다. 그러나 본문을 못 읽은(403) `techblog.gccompany.co.kr`(여기어때) 글을 "우아한형제들(GC company 블로그)"로 소개했다. 회사를 잘못 붙인 인용으로 채점 항목에 넣는다

### M6 검색 잡음 항목 분석 (2026-10-07)

`mcp` 조건 실행 기록으로 세 항목이 답변에 영향을 줬는지 봤다. 잡음은 검색 결과에 실제로 섞였지만 에이전트가 걸러 답변까지는 거의 가지 않았다. M7에서 MCP가 진 원인(사례 절이 설계 내용을 밀어냄)과도 무관하고, 고치려면 사용자 사전·색인 재빌드·`SCHEMA_VERSION`·E9 재평가·새 DB Release가 필요해 **고치지 않는다** (사용자 결정).

- **"대기열"**: 에이전트가 t01·t17의 6회 모두 `대기열`로 검색했다. `search("대기열 시스템", problem_type="트래픽 급증 대응")`은 10건 중 Datadog 모니터링·B마트 출고 최적화처럼 "대기"만 맞은 글이 섞였다. 그러나 t17의 3회 모두 관련 글(네이버페이 대기열 개발기) 하나만 인용했다
- **"캐시"·"캐싱"**: 필터 `캐싱` + 검색어 `캐시`로 기준을 넘은 결과가 15건(t03), 12·44건(t18)으로 넓었지만, 인용한 글은 토스 캐시 적용기·카카오페이 로컬 캐시·올리브영 로컬 캐시+Redis로 모두 주제에 맞았다
- **무관 카드 비율**: 105회에서 카드로 본 항목 1,495개 중 `get_details`로 연 것 333개(22%), 답변에 링크로 인용한 것 395개(26%). 라벨이 있는 과제에서 인용한 글을 M5 라벨로 보면 관련 138 · 일부 관련 46 · 무관 31(판정된 것 중 14%) · 미판정 25. 무관 31건 중 9건은 t22(Unity 게임 서버, 없는 주제), 6건은 t19(집계 예시가 검색어 라벨과 맞지 않음)로, 세 잡음 항목과는 관계없다

## 후속: 호출 판단 개선 (2026-10-19, 이슈 #30)

Claude Code는 MCP 도구 정의를 지연 로드한다(tool search). 세션 시작 때는 도구 이름과 서버 안내(instructions)만 보이고, 도구 설명은 ToolSearch로 불러온 뒤에 보인다. 그래서 부를지 판단하는 문구를 서버 안내로 옮기고, M7이 재현하지 못한 조건(다른 도구와 경쟁, 작업 도중의 설계 판단)에서 호출률을 쟀다.

### 바꾼 것

- **서버 안내**: 무엇인지·언제 부르는지·언제 부르지 않는지만 담는다(400자 → 약 490자). 호출 신호에 구현 중 방식 선택, 기술 비교, 사례 질문, 장애 회고·운영 개선을 더했다. 인용 규칙·사례 활용 원칙은 호출 전에 불러오는 `search` 설명에만 둔다 (사용자 결정, [기획.md](../기획.md#호출-유도))
- **`search` 설명**: 호출 시점을 서버 안내와 맞추고, 검색어가 외부 API로 나가니 사내 코드·고객 이름·비밀 값을 넣지 말라는 안내를 더했다. 인용 규칙은 한 문단으로 합쳤다
- **결과 끝 안내**: `search`·`get_details` 결과마다 붙던 인용·사례 활용 안내를 뺐다. 응답의 약 3.7%라 크기 효과는 작고, 같은 문구가 세 곳에 반복되던 것을 정리한 것이다. 결과 없음·적음 같은 상태 안내는 남겼다
- **README 지시문 스니펫**: 사용자가 `CLAUDE.md`에 복사해 넣던 스니펫(README 간소화 때 빠짐)은 되살리지 않는다. 옛 스니펫의 "설계를 시작하기 전에"처럼 사용자 파일에 남은 지시는 서버 안내를 고쳐도 낡은 채 남는다 (사용자 결정, [기획.md](../기획.md#호출-유도))
- **응답 크기 측정**(평가셋 62개, 단어 일치 검색): `search` 중앙값 3,652자(최대 5,399), `get_details` 5건 중앙값 9,555자(최대 14,107)로 Claude Code 경고 기준(1만 토큰)보다 작다. 상세의 44.5%는 근거 발췌다. 응답 형식은 바꾸지 않았다

- **세션 컨텍스트**(호출률 평가 156회 로그, 요청마다 입력 + 캐시 생성 + 캐시 읽기 토큰): 첫 요청은 두 버전 모두 약 22.5k 토큰이고 서버 안내 변경으로 약 90 토큰 늘었다. 실행이 끝날 때 컨텍스트는 약 41~44k 토큰이다
  - sonbae 정의를 ToolSearch로 불러오는 단계가 약 4k 토큰(경쟁 조건 중앙값, 에이전트 출력 포함)이고 세션에 한 번이다
  - sonbae 응답은 실행마다 경쟁 조건 약 11~15k, 작업 도중 약 6k 토큰으로 **마지막 컨텍스트의 13~37%**다. 호출 1회당 `search` 약 3.3~3.6k, `get_details` 약 6.7~6.9k 토큰
  - 변경 후 경쟁 조건의 응답 합이 늘어난 것(10.7k → 14.8k)은 호출이 늘어서다(전체 `search` 90 → 111회). 호출 1회당 `search`는 3,589 → 3,336 토큰으로 줄었다
- **해석**: sonbae가 쓰는 컨텍스트는 대부분 응답이고, 정의와 서버 안내는 작다. 세션 전체는 모델 컨텍스트 한도보다 한참 작지만, 설계 질문 한 번에 응답이 컨텍스트의 3분의 1까지 차지한다. 가장 큰 단위는 `get_details`(1회 약 6.9k 토큰, 상세 글자의 44.5%가 근거 발췌)다. 응답 형식을 줄이는 최적화는 검색·인용 품질과 맞바꾸는 결정이라 별도 이슈로 다룬다 (아래 이슈 #36)
- 한계: 단계별 증가분에 에이전트 출력(생각, 도구 호출 블록)이 섞여 도구별 토큰은 위쪽으로 잡힌 값이다. 응답 크기는 단어 일치 검색이라 의미 검색과 결과 건수가 다를 수 있다

## 후속: get_details 응답 줄이기 (2026-10-20, 이슈 #36)

이슈 #30 컨텍스트 측정에서 가장 큰 단위가 `get_details`(1회 약 6.9k 토큰, 그중 45%가 근거 발췌)였다. 줄일 후보와 품질을 맞바꾸는 점을 따져 `get_details`만 바꿨다. 결정과 근거는 [기획.md `get_details`](../기획.md#get_details).

### 바꾼 것

- **`get_details`**: 근거 발췌와 문제 유형·도메인·기술·태그 줄을 뺐다. 제목·회사·발행일·원문 링크, 필드별 요약 전체, 같은 글의 다른 항목은 남는다. `evidence` 옵션은 두지 않았다 (사용자 결정)
- **도구 설명·서버 안내·`/sonbae`**: 근거 문장을 인용하라는 안내를 빼고 "요약만 있으니 결과에 없는 세부는 원문 링크를 안내"로 바꿨다
- **`search`는 그대로 둔다**: 카드의 원문 링크는 빼지 않고(사용자 결정), 문제 유형·도메인도 남긴다. 하위 카드를 한 줄로 줄이는 안은 6~10위 카드가 M7 인용의 약 24%를 차지해 이번에 하지 않았다

### 결정 전에 확인한 것 (실행 기록, Voyage 없음)

- 받은 근거 중 답변에 쓰인 것은 M7 66/3,607(1.8%), 이슈 #30 41/2,757(1.5%). 근거에만 있는 내용을 하나라도 쓴 실행은 40~47%였고, 대부분 문장을 옮기지 않고 세부 사실을 고쳐 쓴 것이었다
- 근거에만 있고 요약에 없는 숫자가 있는 포인트는 459개(한 자리 수·연도 제외, 전체 11,353개의 4%). 무작위 24개 중 의미 있는 수치는 5개(주로 개선 전 값)
- 응답 크기(평가셋 62개, 상위 5건): `get_details` 중앙값 9,452 → 4,285자(−54.7%), `search`는 변화 없음 (`eval/runs/context/issue36.json`)

### 에이전트 평가

[eval/agent_format_run.py](../../eval/agent_format_run.py)로 M7 mcp 조건과 같은 환경에서 변경 전(`af1553b`)·후 서버를 따로 설치해 돌리고, [eval/agent_format_eval.py](../../eval/agent_format_eval.py)로 채점했다. 과제는 M7 중 `search`·`get_details`를 쓰는 32개(design·open·absent·noise·few), 버전별 3회, 192회. 모델 sonnet, 오류 0, 대체 검색 0. 서버 연결이 늦어 도구를 못 쓴 1회는 다시 돌렸다. Voyage 검색 약 480회(시험 실행 포함, 약 10.4M 토큰), Claude 비용 표시 약 $22, gpt-5.5 판정 약 $34(시험 실행 포함).

- **근거 없음이 늘었지만 지어낸 수치·방법은 없었다.** 변경 후 15건은 "그 글에는 X가 없다" 같은 부재 주장 6, 사례에 덧붙인 해석 6, 판정 데이터에 카드의 기술명이 빠져 생긴 오판 1, 사실과 어긋남 2였다
- **답변 품질은 나빠지지 않았다.** 변경 후가 42승 24패(부호 검정 p = 0.036)로 앞섰지만, 같은 조건 반복의 변동 폭을 재지 않았고 형식 변경이 답변을 낫게 만든 이유도 확인하지 않아 개선으로 결론 내리지 않는다
- **컨텍스트**: 실행마다 sonbae 결과 글자 수 중앙값 12,420 → 9,338자(−25%). `get_details` 호출 수는 실행당 0.79 → 0.83회로, 상세를 더 자주 열어 줄어든 양을 되먹지 않았다
- 판정 방법: 충실도는 실행마다 도구 결과에 나온 모든 항목의 요약 + 발췌를 기준으로 답변의 사례 서술을 하나씩 판정한다(버전 이름은 주지 않음). 시험 실행에서 링크로 인용한 글만 넘기면 링크 없이 회사명으로 서술한 사례를 근거 없음으로 잘못 판정해 기준을 넓혔다. 답변 품질은 M7 판정기를 두 순서로 돌려 같을 때만 승패로 셌다
- 한계: 모델은 sonnet 하나, 회당 3회다. 충실도 판정기는 요약·발췌만 보므로 "글에 X가 없다"는 부재 주장을 확인하지 못한다. 앞서 "카드만 보고 인용 16%"로 셌던 값은 같은 글의 다른 항목까지 따로 센 것이라 글 기준으로 다시 셌다(M7 2%)
