# M9. 원격 HTTP 서버 (확장)

> 상태: **완료** (2026-10-19) · 직무 근거: 백엔드 · 허브: [docs/README.md](../README.md)

M8의 데이터 배포 구조를 재사용하므로 M8 다음에 한다.

## M8에서 넘어온 항목

- **DB 준비**: 원격 서버도 M8 4단계 방식(`db.cached_db`, `db.check_for_update`)으로 최신 Release DB를 하루 한 번 확인해 받는다. ~~원격 서버는 오래 떠 있으므로 실행 중 교체가 필요한지 착수 시 정한다~~ → 서버를 필요할 때만 켜고 꺼서 실행 중 교체는 하지 않는다 ([기획.md](../기획.md#원격-http-서버-m9))
- **PyPI 전환 보류의 전제**: 설치 없이 URL로 연결하는 원격 서버가 설치 편의 문제를 해결한다는 판단으로 PyPI 전환을 보류했다 ([기획.md](../기획.md#배포-로드맵))

## 작업

- stdio는 유지하고 Streamable HTTP 방식을 추가해 클라우드에 배포
- 요청 제한, 구조화 로깅, 지연 시간 모니터링

## 완료 기준

URL만으로 연결해 쓸 수 있음.

## 결정

- 호스팅은 Fly.io(shared-cpu-1x 1GB), 실제 사용자를 받지 않고 필요할 때 켜고 끈다 (2026-10-18, [기획.md](../기획.md#원격-http-서버-m9))
- 서버가 Voyage 키를 보관하고(Fly.io 시크릿), 토큰 하나를 `Authorization: Bearer`로 확인한다 (2026-10-18, 같은 곳)
- 요청 제한은 프로세스 메모리의 분당 한도(넘으면 429), 상태 없는 세션(`stateless_http`)과 `GET /health`(준비 전 503)를 두고, DB는 기동 때 최신 Release를 받는다 (2026-10-18, 같은 곳)

## 진행 기록

### 착수 분석 (2026-10-15~18)

- SDK(mcp 2.2.0)의 `MCPServer.run()`이 `transport="streamable-http"`, `stateless_http`, `host`/`port`를 지원해 전송 방식 추가는 작다. 도구 호출마다 DB 연결을 여는 구조(#22)라 동시 요청에도 안전하다
- 준비를 마친 서버는 메모리 약 590MB, 준비 7초(로컬 Windows 측정). 512MB 등급은 부족하다
- 착수 결정은 모두 정했다(위 "결정"). 다음은 구현

### 1단계: HTTP 진입점 (2026-10-18)

- `sonbae.remote`와 명령 `sonbae-http` 추가. `server.py`의 도구를 상태 없는 Streamable HTTP(`/mcp`, JSON 응답)로 연다. 주소는 `SONBAE_HOST`(기본 127.0.0.1)·`PORT`(기본 8000)
- 테스트(`tests/test_remote.py`)는 실제 uvicorn을 띄우고 MCP 클라이언트로 URL에 연결해 도구 목록·검색 결과가 stdio 호출과 같은지, 동시 연결 8개가 섞이지 않는지 본다
- 실제 DB로 띄워 URL로 연결해 검색까지 확인(연결·목록·검색 0.2초)

### 2단계: 토큰 인증 (2026-10-18)

- `remote.TokenAuth` ASGI 미들웨어: `SONBAE_TOKEN`이 있으면 `Authorization: Bearer <토큰>`이 정확히 맞는 HTTP 요청만 통과, 나머지는 401과 `WWW-Authenticate: Bearer`. 상수 시간 비교(`hmac.compare_digest`). 응답 스트림을 막지 않도록 BaseHTTPMiddleware가 아니라 ASGI로 직접 감쌌다
- 토큰 없이 로컬이 아닌 주소로 열면 DB 준비 전에 기동을 멈춘다
- 테스트: 토큰 없음·틀림·형식 오류(`Bearer` 없음, `Basic`) 401, 맞는 토큰으로 MCP 클라이언트 검색, 토큰 없는 외부 기동 거부. 실제 기동에서도 curl로 401·401·200과 기동 거부를 확인

### 3단계: 요청 제한 (2026-10-18)

- `remote.TokenBucket`과 `remote.RateLimit` ASGI 미들웨어: 인증을 통과한 `/mcp` 요청을 토큰 버킷(기본 분당 60회, 몰림 20회)으로 세어 넘으면 429와 `Retry-After`. 미들웨어 순서는 인증 → 요청 제한 → MCP라 틀린 토큰은 세지 않는다. 이벤트 루프 안에서 await 없이 세므로 잠금은 두지 않았다
- 테스트: 가짜 시계로 몰림·다시 참·쉬어도 몰림 이상으로 쌓이지 않음, 실제 서버로 한도 초과 429·`Retry-After`, 틀린 토큰이 한도를 쓰지 않음
- 추천값 실험(실제 기동, 로컬):

| 실험 | 결과 |
| --- | --- |
| 즉시 30회 몰림(`tools/list`) | 20회 성공, 10회 429 (몰림 허용만큼 통과) |
| 에이전트 패턴: 연결 하나로 검색 5개 병렬 × 3번(실제 Voyage) | 15회 모두 성공, 단어 일치 대체 0, 3.7초 |
| 초당 2회 30초 지속 | 49회 성공, 11회 429 (처음 차 있던 20 + 초당 1개씩 30) |

- 연결 하나로 부르면 검색 하나가 HTTP 요청 하나로 세진다(연결할 때 initialize 등 1~2회 추가)

### 4단계: 헬스 체크 (2026-10-18)

- `server.readiness`: 기동 준비 두 단계(DB·항목 임베딩, 형태소 분석기)의 완료·실패를 기록한다. 실패 이유는 경고 로그로 남긴다
- `GET /health`(`remote.health`, SDK `custom_route`): 모두 끝나면 200 `ok`, 아니면 503 `starting`/`error`와 단계별 상태. 인증·요청 제한에서 뺐다
- 테스트: 준비 전 503 `starting` → 준비 후 200, DB가 없으면 503 `error`(응답에 경로 없음), 토큰 없이 불러도 되고 여러 번 불러도 요청 한도를 쓰지 않음
- 실제 기동: 프로세스 시작 4.6초 뒤 200(로컬, 파일 캐시가 따뜻한 상태). 처음 측정한 준비 7초를 감안해 `fly.toml`의 `grace_period`는 15초 이상으로 둔다

### 5단계: 구조화 로깅 (2026-10-18)

- `sonbae.logs`: 루트 로거가 JSON 한 줄씩 표준 출력에 쓴다(시각, 수준, 로거, 메시지, `request_id`, 추가 필드). uvicorn 로그도 모으고 uvicorn 접근 로그는 끈다
- `remote.RequestLog` 미들웨어(가장 바깥): 요청마다 `http_request`(방식, 경로, 상태 코드, `duration_ms`). 401·429도 남고 정상 헬스 체크는 뺀다. `Fly-Request-Id`가 있으면 요청 ID로 쓴다
- `server._tool_log`: 도구 호출마다 `tool_call`(도구, `duration_ms`, `ok`/`error`, 검색은 `mode`·`fallback`·`results`·`query_chars`·필터, 상세는 요청·찾은·없는 수). 도구는 작업 스레드에서 돌지만 contextvar가 넘어가 같은 `request_id`로 묶인다
- stdio 서버는 SDK가 INFO 로그를 표준 오류로 내게 설정해 `tool_call`이 찍혔다. `server.main`에서 `sonbae` 로거를 경고 이상으로 두어 예전처럼 조용하게 했다
- 테스트: 요청·도구 로그가 같은 요청 ID, 검색어 원문이 로그에 없음, 401 기록과 `Fly-Request-Id` 사용, 정상 헬스 체크 미기록, 실패한 도구 호출 기록, JSON 형식과 httpx INFO 억제
- 실제 기동 확인: 검색(의미 검색, 1,397ms, 결과 10)·상세(2ms)·집계(185ms)·401 요청이 기대한 필드로 남았다
- 사용자 지정 지표(Prometheus `/metrics`)는 미뤘다 ([기획.md](../기획.md#원격-http-서버-m9))

### 6단계: 컨테이너와 Fly.io 설정 (2026-10-19)

- `Dockerfile`: `python:3.13-slim` + uv 0.12.19, `uv sync --locked --no-default-groups`로 서버 의존성만 설치, 루트가 아닌 사용자로 `sonbae-http` 실행(`0.0.0.0:8080`). 검색 DB는 넣지 않는다. `.dockerignore`는 서버 패키지 파일만 남긴다
- uv 다운로드 캐시가 설치 층에 남아 의존성 층이 832MB(가상환경은 260MB)였다. `UV_NO_CACHE`로는 줄지 않아 캐시를 빌드 캐시 마운트(`--mount=type=cache`)로 옮겼고, 의존성 층 275MB, 이미지 압축 크기 566MB → 192MB
- `fly.toml`: 도쿄(`nrt`), shared-cpu-1x 1GB, `auto_stop_machines`/`auto_start_machines`(요청이 없으면 멈춤, 최소 0대), 동시 요청 soft 20·hard 50, `/health` 확인(15초 간격, 유예 30초)
- 로컬 컨테이너 확인(메모리 1GB 제한): 기동부터 `/health` 200까지 17초(형태소 분석기 3.3초, DB 다운로드 2.2초, 모듈 로딩 1.3초가 서버 기동과 겹침), 메모리 574MB. 토큰으로 검색(의미 검색 1.1초)·상세·집계 정상, 틀린 토큰 401, JSON 로그 정상

### 7단계: Fly.io 배포 (2026-10-19)

- flyctl v0.4.118 설치, 가입·결제 수단 등록(사용자), 앱 `sonbae`(조직 personal) 생성
- 접속 토큰을 새로 만들어 `.env`(git 제외)의 `SONBAE_TOKEN`에 두고, 토큰·Voyage 키를 값 출력 없이 `fly secrets import`로 등록
- `fly deploy --ha=false`: 원격 빌드 이미지 180MB, 도쿄(`nrt`) 머신 1대, 공유 IPv4(전용 IPv4 요금 없음)·전용 IPv6, 헬스 체크 1/1 통과
- URL 확인(로컬 PC → 배포한 앱의 `/mcp`): 연결 0.37초, 의미 검색 3회 0.50~0.74초(대체 없음), 상세 0.05초, `/health` 0.3~0.4초, 틀린 토큰 401. 의미 검색이 로컬 실행(1.1~1.4초)보다 빠른 것은 Voyage API까지의 왕복이 데이터센터에서 더 짧아서로 보인다
- Claude Code에 `sonbae-remote`(HTTP, Bearer 헤더, 이 프로젝트 범위)로 등록해 연결됨을 확인했다. 새 세션에서 도구를 실제로 써 보는 확인은 남았다

### 8단계: 정지 후 첫 요청 지연 (2026-10-19)

- 측정: `fly machine stop`으로 멈춘 뒤, 첫 요청(연결 + 검색)으로 깨워 시간을 쟀다(로컬 PC → 도쿄)
- 처음 6회 중 1회는 연결이 실패했다. 로그에 프록시의 `failed to connect to machine: gave up after 15 attempts (in 8.2s)`가 남았고, 서버는 프로세스 시작 뒤 포트를 열기까지 8.5초가 걸렸다. 기동 준비 스레드를 포트 열기보다 먼저 시작해 CPU 1개를 두고 다퉜기 때문으로 보았다
- 수정: `remote._PrepareAfterBind`(uvicorn `Server.startup` 뒤에 `server._prepare()`)로 포트를 연 다음 준비를 시작한다. 준비 시작은 1초 미만 늦어질 뿐이고, 형태소 분석기는 잠금으로 한 번만 불러오며 그동안 검색은 서버 안에서 기다린다. 테스트: 준비를 시작하는 순간 이미 포트에 접속되는지
- 수정 후(5회 모두 성공):

| 회 | 연결(기동 포함) | 첫 검색 | 두 번째 검색 | 합계 |
| --- | --- | --- | --- | --- |
| 1 | 13.9초 | 1.1초 | 0.84초 | 15.0초 |
| 2 | 14.6초 | 1.2초 | 0.62초 | 15.8초 |
| 3 | 13.9초 | 1.1초 | 0.67초 | 15.0초 |
| 4 | 14.6초 | 0.9초 | 0.61초 | 15.5초 |
| 5 | 13.8초 | 1.0초 | 0.95초 | 14.9초 |

- 수정 전(성공한 5회)도 합계 15.3~15.9초로 거의 같았다. 지연의 대부분은 포트가 아니라 준비 시간이다. 로그 기준: 머신 시작 1.3초 → 포트 열림 +2초 → 준비 중 `/health` 503 약 10초(프록시는 헬스 체크가 통과할 때까지 요청을 붙잡는다) → 통과 1초 뒤 응답. 준비는 DB 다운로드·형태소 분석기·항목 임베딩이고 shared-cpu 1개에서 로컬보다 느리다
- 수정 후에도 프록시 로그에 같은 `gave up` 경고가 한 번 남지만 요청은 다시 시도돼 성공했다. 수정 전 실패 1회의 정확한 원인은 확인하지 못했고, 수정 후 5회에서는 다시 나지 않았다
- 켜진 뒤의 검색은 0.6~0.95초
- 켜고 끄기는 자동 정지·시작으로 유지하고, DB를 이미지에 넣는 안은 택하지 않았다 ([기획.md](../기획.md#원격-http-서버-m9))

### 9단계: Claude Code 실사용 (2026-10-19)

- 새 Claude Code 세션(`claude -p`, 도구는 `sonbae-remote`의 search·get_details만 허용)에 "선착순 쿠폰 중복 발급 방지 사례 2개를 회사명·원문 링크와 함께 요약"을 요청했다
- 에이전트가 원격 search를 불러 토스(RedLock 분산 락)·올리브영(이중 카운터) 사례를 원문 링크와 함께 답했고, 사례의 한계(올리브영은 미발급 방지가 핵심)도 짚었다. 2턴, $0.15
- Fly.io 로그에 같은 시각 `tool_call`(search, 의미 검색, 결과 9건, 572ms)이 남아 원격 서버를 거친 것을 확인했다

### 후속: 원격 부하 측정 ([이슈 #27](https://github.com/zie-ning/sonbae/issues/27), 2026-10-19)

- 측정: 로컬 PC → 도쿄, MCP `tools/call`을 직접 보내고(상태 없는 서버라 initialize 없이 됨) 서버 `tool_call` 로그와 맞춰 봤다. 콜드 스타트는 8단계에서 쟀으므로 켜진 머신만 쟀다
- 켜진 상태 순차: 상세 0.06~0.08초, 집계 0.28~0.34초, 검색 0.48~0.71초
- 일꾼 4개일 때 동시 검색(요청 제한 몰림 20 안): 동시 4/8/16/20개가 전체 1.3/1.9/3.1/3.2초로 거의 선형으로 늘었다. 서버 `tool_call`도 1.4~2.7초라 지연은 서버 안에서 생겼다
- 원인(로컬, CPU 1개로 묶어 같은 코드 실행): 동시 32개에서 Voyage 일꾼 앞 대기가 임베딩 0.84초 + 리랭커 1.88초(p50), 실제 HTTP는 0.2~0.4초씩, 검색 스레드 CPU는 16ms. 일꾼 32개면 대기 0, 전체 4.75초 → 1.36초
- 일꾼 32개로 배포하고 요청 제한을 잠시 풀어 잰 결과(측정 뒤 기본값으로 되돌리고 몰림 20 초과가 429인 것을 확인):

| 부하 | 결과 |
| --- | --- |
| 동시 20 / 32 / 40 / 48 / 64개 | 전체 1.6 / 1.6 / 2.1 / 2.0 / 2.9초, 모두 의미 검색 |
| 초당 2회 60초 | 120건 모두 의미 검색, p50 0.59초 |

- 원인: Voyage 계정 한도다. 검색 1회는 임베딩 약 10토큰, 리랭커 약 21.7k 토큰(후보 50건, 실측 5회 평균 21,755)을 써서 요청 수(모델별 2,000 RPM)가 아니라 rerank-3 토큰 한도(TPM)에 먼저 걸린다. 계정은 등급 1이라 공식 한도는 2M TPM, 검색 분당 약 92회다
- 실측에서는 분당 약 240회(약 5.2M 토큰)까지 429가 나지 않았고 약 275회(약 6.0M 토큰)에서 처음 났다. 공식 한도의 약 3배까지 통과한 셈인데, Voyage가 지금 느슨하게 적용할 뿐이라 설계는 공식 한도(분당 약 92회)에 맞춘다. 순간 몰림(동시 64개)에는 걸리지 않고 분 단위 누적에서 걸렸다
- 지금 요청 제한은 지속 분당 60회(검색당 평균 21.7k 토큰 기준 약 1.3M TPM, 공식 한도의 65%)이고, 버킷이 찬 상태에서는 몰림 20회가 더해져 60초 동안 최대 약 80회(약 1.74M TPM, 약 87%)까지 통과한다. 둘 다 공식 한도 아래라 정상 운영에서는 429가 나지 않는다(토큰은 실측 평균이라 긴 항목이 몰리면 더 클 수 있다). 서버 한 대의 처리 능력(동시 64개 2.9초)은 이보다 훨씬 커서, 상한은 서버가 아니라 리랭커 토큰이다. 토큰 줄이기는 [이슈 #32](https://github.com/zie-ning/sonbae/issues/32)
- 429가 나면 연속 실패 차단이 30초 동안 모든 검색을 단어 일치 검색으로 돌린다. 한도를 넘는 동안 Voyage를 더 두드리지 않는 의도한 동작이다
