# 기술블로그 사례 검색 MCP 서버 기획

## 개요

코딩 에이전트가 개발 중에 국내 기업의 실제 해결 사례를 참고해 설계 판단을 하도록 돕는 사례 검색 MCP 서버.
국내 IT 기업 기술 블로그를 수집해 **문제 상황 / 해결 방법 / 성능·운영 포인트**(+ 글에 명시된 버린 대안)로 구조화하고, Claude Code·Cursor 같은 코딩 에이전트가 MCP 도구로 호출해 비슷한 사례를 받아보게 한다. 사용자가 검색하러 오는 게 아니라, 개발하는 곳으로 사례가 찾아가는 구조다.

## 문제 정의

코딩 에이전트는 설계 판단을 일반론으로 하고, 좋은 실무 사례는 흩어져 있어 개발 도중에 찾기 어렵다.

- **에이전트의 근거 부족**: "선착순 쿠폰 동시성" 같은 문제에 트래픽 규모나 트레이드오프 없이 교과서적인 답을 낸다. "A사는 X를 썼다" 같은 사례를 지어낼 위험도 있다.
- **사례의 분산**: 좋은 사례는 기업 블로그마다 흩어져 있고, 블로그 자체 검색은 제목 수준이며, 구글 검색에는 SEO용 짜깁기 글이 섞인다.
- **모르는 걸 모름**: 비슷한 문제를 누가 풀었는지 모르면 찾아볼 생각조차 못 한다. 물어보는 챗봇(pull)보다 개발 흐름 안에서 제시되는 방식(push)이 필요하다.

## 차별점

답변을 만드는 LLM은 같으므로, 차이는 검색과 데이터 구조에서만 난다. 사례·집계형 질문에서는 이기고, 개념 질문과 DB 밖 주제에서는 진다.

| 질문 유형 | LLM 단독 | 웹검색 LLM | 이 서비스 |
| --- | --- | --- | --- |
| 개념 ("Redis 분산락 원리") | 충분함 | 충분함 | 비슷하거나 열세 |
| 사례 ("쿠폰 동시성 어떻게 풀었나") | 지어낼 위험 | 2~3개 사례 | 더 많은 사례를 구조로 비교 |
| 집계 ("Kafka 쓰는 국내 회사") | 못함 | 부정확 | 확실히 우위 |
| DB에 없는 주제 | 답은 함 | 잘함 | 못함 |

핵심 강점은 세 가지다.

- **구조화된 사례 데이터**: 문제 상황·해결 방법·성능/운영 포인트로 정리하고, 글에 명시된 경우 버린 대안까지 담아 에이전트가 바로 설계 판단에 쓸 수 있다. 기술·문제 유형·버린 대안별 집계도 제공한다.
- **출처 품질**: 기업 기술 블로그만 사용하고 모든 사례에 원문 링크와 근거 발췌를 붙인다.
- **개발 흐름 안 제공**: 검색 1회로 빠르고 싸게, 에이전트가 필요할 때 직접 호출한다.

챗봇 자체는 웹검색 LLM과 큰 차이가 없으므로 핵심 가치로 내세우지 않는다.

### 유사 서비스: velopers.kr

국내 기업 기술 블로그 155곳을 모아 AI로 요약하는 웹 서비스. 글 유형에 따라 "문제 상황 / 원인 분석 / 해결 방법" 또는 "핵심 내용 / 적용해볼 점"으로 요약하고 기술 태그를 붙인다. 이 프로젝트의 유형별 구조는 이 방식을 참고했다.

| | velopers.kr | 이 서비스 |
| --- | --- | --- |
| 사용자 | 사람이 사이트에 와서 읽음 (pull) | 코딩 에이전트가 개발 중에 호출 (push) |
| 제공 방식 | 웹 목록·검색 | MCP 도구 (검색, 상세, 집계) |
| 집계 | 태그별 글 수 | 기술·문제 유형·버린 대안별 사례 수와 회사 수 |
| 근거 | 요약 | 요약 + 필드별 원문 발췌 (원문 존재 여부 자동 검증) |

### 서비스 이름과 로고 (2026-10-14)

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 이름 | `sonbae` (선배) | "이 문제, 선배들은 어떻게 풀었지?"라는 서비스 개념을 한 단어로 담는다. 표준 로마자 표기 `seonbae`보다 짧아 설치 명령·MCP 설정 키로 쓰기 편하다 |
| 로고 | `sonbae` 워드마크에서 o 자리를 틸(`#1D9E75`) 돋보기로 바꾼 형태 ([sonbae-wordmark.svg](assets/sonbae-wordmark.svg)) | 이름과 "검색 도구"라는 기능을 한 번에 전달한다. 심볼형(발자국·말풍선 등)도 검토했으나 워드마크를 골랐다 |
| 슬로건 | 로고와 함께 쓰지 않음 | 로고는 이름만으로 단순하게 유지 |

- 로고는 README 헤더와 저장소 소셜 프리뷰에 쓴다. 정사각형 아이콘(돋보기만 뗀 버전)은 파비콘이나 조직 계정이 필요해질 때 만든다.
- 글꼴은 Pretendard Medium(SIL OFL)이고, 글자를 패스로 바꿔 넣어 보는 환경의 글꼴과 상관없이 같은 모양으로 보인다. 돋보기 크기·선 굵기·간격은 첫 시안의 비율을 따른다(사용자 결정: o에 꽉 맞춘 버전보다 가볍고 여유 있는 첫 시안을 고름).
- 파일은 두 형식이다. README·웹에는 SVG([sonbae-wordmark.svg](assets/sonbae-wordmark.svg), 다크 모드에서 글자색이 밝게 바뀜)를, 소셜 프리뷰처럼 SVG를 못 쓰는 곳에는 투명 배경 PNG(너비 1200px)를 쓴다. 밝은 배경용 [sonbae-wordmark-light.png](assets/sonbae-wordmark-light.png), 어두운 배경용 [sonbae-wordmark-dark.png](assets/sonbae-wordmark-dark.png).
- **코드·배포 이름도 `sonbae`로 바꾼다** (사용자 결정, 2026-10-14). 저장소 `zie-ning/sonbae`, 패키지 `sonbae`, 실행 명령 `sonbae`, MCP 서버 이름과 prompt `/sonbae`, 환경 변수 `SONBAE_DB`·`SONBAE_CACHE_DIR`, 캐시 폴더 `sonbae`.
  - 옛 환경 변수와 캐시 폴더는 지원하지 않는다. 사용자가 적은 지금이 바꾸기 가장 쉽고, 옛 캐시는 첫 실행 때 DB를 다시 받으면 된다.
  - 크롤러 User-Agent 이름 `TechblogCaseBot`은 유지하고 URL만 바꾼다. 우아한형제들에 수집 허락을 받은 봇 이름이기 때문이다.
  - 그대로 두는 것: DB·Release 파일 이름 `techblog.sqlite`(바꾸면 기존 Release와 맞지 않아 재배포가 필요하고 사용자에게 보이지 않음), LangSmith 프로젝트·데이터셋 이름, 에이전트 평가(`eval/agent_run.py`)의 서버 등록 이름 `techblog`(과거 기록과 비교). 마일스톤 진행 기록과 eval 결과의 옛 이름도 당시 기록이라 고치지 않는다.

### README 포지셔닝 (2026-10-14)

- **README는 "사례를 찾을 거라면 웹 검색보다 sonbae가 낫다"를 축으로 쓴다** (사용자 결정). 에이전트에게 웹 검색으로 사례를 찾게 하면 SEO 블로그·커뮤니티 글·짜깁기 요약이 섞인다는 점을 개발자 대부분이 겪어 봤기 때문이다. 근거는 M7의 `web-ask` 비교(61승 20무 24패)와, 같은 질문을 웹 검색·sonbae로 한 번씩 실행한 데모([eval/reports/readme-demo.md](../eval/reports/readme-demo.md))다.
- M7의 도구 없음 비교(6승 80패)는 README에 쓰지 않는다. 사용자는 이 결과를 채점 설계 문제로 본다(사례에 분량을 쓴 답을 감점하는 채점 지시문).
- 구성: 히어로(로고, "이 문제, 선배들은 어떻게 풀었지?", 데모 GIF) → 웹 검색 대비 비교표 → 두 줄 설치(클라이언트별 설정·Voyage 키는 접기 블록) → 질문 예시와 도구 표 → 데이터 출처·라이선스. 개발 내용은 [개발.md](개발.md)로 옮긴다.
- **README는 짧게 유지한다** (사용자 결정, 2026-10-14). 사용자가 직접 간소화하면서 데모 비교표·답변 발췌, 실제 검색 결과 카드, 한계, 문제 해결, 개발 문서 링크를 뺐다. 데모 비교의 근거는 [eval/reports/readme-demo.md](../eval/reports/readme-demo.md)에 남아 있다.
- 데모와 결과 카드는 지어낸 예시가 아니라 실제 실행 출력만 쓴다. 한국어만 둔다.

### 구조화(추출)

| 항목 | 결정 |
| --- | --- |
| 추출 LLM (M3 확정) | OpenAI API, **`gpt-5.6-luna` (reasoning effort medium)**. M3에서 같은 프롬프트(v4)로 후보 6개(gpt-5-mini medium·low·high, gpt-5.6-luna, gpt-5.4-mini, gpt-5.6-terra)를 파일럿 80편에 추출하고 정답 24편으로 채점해 정함. luna는 전체 1,262편 추정 비용이 $5.3(gpt-5-mini $17.4, 상위 모델 terra $48.7)으로 가장 싸면서 품질은 terra와 비슷함: 추출 여부 정확 일치 100%, 완결성 78%(mini 61%), 도메인 정밀도/재현율 94%/96%, 충실성 4.89, 분할 4.62. gpt-5-mini가 프롬프트를 고쳐도 틀리던 분류 기준(조직 문화 글, 도구 장려 제도 글, 개념 글, 발표 소개 글 제외)을 모두 지킴. 같은 설정 2회 실행에서 gpt-5-mini는 추출 여부 일치 92% ↔ 79%, 분할 4.39 ↔ 3.62로 흔들렸지만 luna는 100% ↔ 100%, 4.62 ↔ 4.44로 안정적. 근거: [eval/reports/eval-step7-models.md](../eval/reports/eval-step7-models.md), [eval/reports/eval-stability.md](../eval/reports/eval-stability.md) |

| 사례·인사이트 구분 폐지 (M3) | 처음에는 사례형(문제 상황 / 해결 방법 / 성능·운영 포인트)과 인사이트형(핵심 내용 / 적용해볼 점)을 나눴으나, M3 정답셋 검수 중 **추출/제외만 판단**하고 구조를 하나로 합치기로 함. 이유: 둘의 경계가 자주 갈림(정답 17편 중 5편이 경계 글), 추출 모델도 같은 프롬프트에서 실행마다 사례 4개 ↔ 인사이트 1개를 오감(코틀린 팁 모음), 사람마다 판단이 갈리는 구분을 `kind` 필터로 쓰면 필터 결과도 믿기 어려움. 구분이 하던 일은 이렇게 옮김: 팁 모음을 잘게 쪼개지 않는 규칙 → 항목 나누기 규칙, 근거의 세기 → 판정 대신 **성능·운영 포인트(적용 결과)가 원문에 있는지**를 카드와 집계에 표시, `kind` 필터 → 제거. 이전 기록은 읽을 때 사례·인사이트를 추출로 바꾸고 인사이트의 핵심 내용·적용해볼 점을 해결 방법으로 옮김 |

"AI 활용 개발" 문제 유형 신설은 하지 않음. **M3 마감 결정**: 목록(문제 유형 20개, 도메인 10개)은 그대로 확정. 다중 선택 전환과 luna 모델로 "개발 생산성"(항목 대비 36%)·"사내 플랫폼·개발 도구"(37%) 쏠림이 줄었고, 0건 분류는 표본 크기 탓으로 봄. 정답셋 라벨링에서 나온 공백 후보 2개(JVM·GC 성능 튜닝, 검색 품질·정확도)와 도메인 축의 "LLM·AI"·"사내 플랫폼·개발 도구" 성격 문제는 M4 전체 추출 결과로 검토. **M4 표본 결정** (블로그당 25편 + M1 20편, 항목 250개): 문제 유형 **"검색·추천·모델 품질"을 추가해 21개**로 한다. 검색 정확도·리랭킹·추천 모델·LLM 품질 평가 글 약 10개 항목이 맞는 유형이 없어 "DB 성능·쿼리 최적화"·"데이터 파이프라인"으로 흩어졌고, 문제 유형이 비어 나온 항목도 생겨서. JVM·GC 튜닝은 주제인 글이 3편 정도(1~2%)라 신설하지 않고 기존 유형과 기술 태그로 찾는다. 도메인 축은 그대로 둔다: "LLM·AI"가 "AI가 제품"과 "AI가 도구"(32개 중 17개가 "사내 플랫폼·개발 도구"와 함께 붙음) 두 의미로 쓰이지만 다중 선택이라 어느 쪽으로 검색해도 찾히고, 집계를 깔끔하게 하려고 검색 정확도를 낮추지 않는다는 "도구 우선순위" 원칙에 따름 |
| 분류 개수 (M3 변경) | **문제 유형 1~3개, 도메인 1~2개를 순서 없이 다중 선택**한다. | 평가·관측 도구 (M3) | **LangSmith**. 추출 과정(분류 → 구조화 → 재시도)을 원문 포함으로 트레이싱하고, 파일럿·정답셋·실패 사례 회귀셋을 Dataset으로, 모델·프롬프트 버전별 추출을 Experiment로 관리하며, 채점기 검증용 사람 검수는 Annotation queue에서 함. 도입 이유: 실패 트레이스 확인 → Playground에서 프롬프트 수정 → 회귀셋 확인으로 프롬프트 개선 주기를 짧게 하고, 원문을 옆에 둔 검수 화면을 직접 만들지 않기 위함. M8 자동 갱신에서 운영 모니터링으로 이어서 씀. 지표 함수와 LLM 채점기는 직접 구현하고 결과는 저장소(`eval/runs/`, `eval/reports/`)에도 남겨 LangSmith 없이 재현 가능하게 함. 트레이싱은 환경 변수로 켜고 기본은 끔 |
| 발췌 검증 실패 처리 (M3에서 현행 유지로 확정) | 공백·줄바꿈·따옴표 모양·대소문자·마크다운 강조 차이와 `...` 중간 생략만 허용하고 나머지는 불일치로 봄. 여러 줄 발췌는 떨어진 문장을 이어 붙인 것으로 보고 줄마다 원문에 있는지 검사. 실패 발췌가 있으면 실패 목록을 알려 주고 **한 번 다시 구조화**한 뒤, 두 시도 중 검증을 통과한 내용이 더 많은 쪽을 씀(재시도가 더 나쁠 때가 있음). 그래도 실패한 항목은 버리고, 해결 방법이 비면 그 항목을 통째로 버림(M3에서 문제 상황은 필수에서 뺌: 팁·활용 경험 글은 문제 상황이 없을 수 있음). 버린 발췌는 글별 기록에 남김. **M3 완화 실험 결과 현행 유지**(사용자 결정): 떨어진 문장을 한 줄로 이은 발췌까지 허용하는 문장 단위 검증은 baseline에서 탈락 50개 중 19개를 살렸지만, 프롬프트에 "떨어진 문장을 잇지 말라"를 넣은 v4에서는 0개였고, 이어 붙인 문장이 맥락을 바꾸는 위험이 있어 채택하지 않음. 남은 탈락은 바꿔 쓴 문장·코드 블록 등이라 재시도로 처리 ([eval/reports/evidence-relax.md](../eval/reports/evidence-relax.md)) |
| 추출 결과 파일 | `data/entries.jsonl`(항목) + `data/posts.jsonl`(글별 기록: 글 유형, 추출 여부, 분류 이유, 원문 해시, 모델, 프롬프트 버전, 항목 ID, 버린 발췌). 제외된 글도 기록해 다시 추출하지 않음. 둘 다 커밋 |
| 프롬프트 버전 기록 | LLM에 전달되는 지시 전체(분류·구조화 지시문, 입력 형식, 재시도 문구, 출력 스키마와 필드 설명)의 SHA-256 앞 12자리를 글별 기록(`posts.jsonl`)의 `prompt_version`에 저장. 사람이 올리는 번호는 잊기 쉬워 자동 해시를 씀. 해시만으로는 내용을 알 수 없으므로 새 버전이 처음 쓰일 때 전문을 `data/prompt_versions/{버전}.md` 스냅샷으로 저장(커밋). 기본 실행은 새 글·원문이 바뀐 글만 추출하고, `--outdated`를 주면 다른 프롬프트·모델로 추출한 글도 다시 추출(프롬프트를 고칠 때마다 자동 전체 재추출하면 비용이 커서 명시적으로 켬) |
| 항목 ID | `case_0001` 형식, 한 번 붙으면 바뀌지 않음. 글을 다시 추출하면 옛 항목을 지우고 새 번호를 붙임(번호 재사용 없음) |
| 기술명 저장 | 정규화된 `technologies`와 원래 이름 `technologies_raw`를 함께 저장. 사전을 보강하면 LLM 재호출 없이 `pipeline.normalize --apply`로 다시 정규화 |
| 기술명 정규화 규칙 | 대소문자·공백·`-_.` 차이 무시. 그대로 없으면 괄호 설명(`OGG(Oracle GoldenGate)`는 괄호 안도 후보)과 끝의 버전 번호(`RabbitMQ 3.12.14`)를 떼고 다시 찾음. 모델 버전은 제품군으로 묶음(`Claude 3.5 Sonnet` → Claude) |
| 버린 대안 이름 | 사전으로 정규화하되, 결과가 그 사례에서 쓴 기술과 같으면 원래 이름을 유지. "Claude 3 Haiku를 버리고 Claude 3.5 Sonnet을 씀"이 "Claude를 버렸다"로 기록되는 모순을 막기 위함 |
| 카드 요약 줄 | 문제 상황·해결 방법의 첫 항목이 `search` 카드에 쓰이므로, 해결 방법 첫 항목은 **최종 채택한** 해결책이어야 함을 프롬프트와 스키마 설명에 명시 (M1 사용 중 버린 대안이 카드에 해결 방법으로 나온 문제에서 나온 결정) |

#### 공통 원칙

- **도구 우선순위 (M3 결정)**: 이 서버의 핵심은 `search`다. 코딩 에이전트에 비슷한 사례를 정확히 찾아 주는 것이 프로젝트의 주된 역할이고, `get_details`는 그 결과를 여는 도구, `aggregate`는 여러 회사의 선택을 비교할 때 쓰는 **보조 도구**로 중요도가 가장 낮다. 데이터 구조·분류·색인을 설계할 때 집계를 깔끔하게 만들려고 `search`의 검색 정확도를 낮추는 선택(예: 집계 중복을 피하려고 분류를 하나만 고르게 강제)은 하지 않는다. 둘이 부딪히면 `search`를 우선하고, 집계 쪽은 결과 표시(예: "건수 합이 전체보다 클 수 있음")로 보완한다
- **결과 형식**: JSON이 아닌 읽기 쉬운 텍스트. 토큰이 적고 에이전트가 답변에 바로 인용하기 쉬움
- **필터 값**: 문제 유형(21개), 도메인(10개)은 입력 스키마의 선택지 목록(`enum`)으로 제공해 에이전트가 정확한 값을 고르게 함. 선택지는 추출에 쓰는 분류 정의 파일에서 자동 생성해 항상 일치시킴. 기술은 종류가 많아 자유 입력으로 받고 서버가 기술 사전으로 정규화함 (예: "카프카" → Kafka)
- **회사·날짜 필터 없음**: 개발 흐름에서 회사나 날짜로 좁혀 찾을 일이 드물고, 데이터가 이미 최근 3년치라 날짜 필터의 효과가 작음. 파라미터가 적을수록 에이전트가 헷갈리지 않음. 대신 회사 이름을 검색 색인에 넣어 "토스 Kafka"처럼 검색어로 찾을 수 있게 하고, 카드에 발행일을 보여 에이전트가 오래된 글을 감안하게 함
- **사전에 없는 기술**: 필터에서 제외하고 그 사실과 비슷한 기술을 결과에 알려 줌
- **결과가 없거나 적을 때**: "이 주제는 사례가 N건뿐"이라고 명확히 알려 에이전트가 사례를 지어내지 않게 함

- 카드의 문제 유형·도메인도 남긴다 (이슈 #36). `search` 결과에서 항목별 분류가 나오는 곳은 카드뿐이고, 에이전트가 다음 검색의 필터를 고르는 단서가 된다. 줄일 효과는 카드의 약 7%다

#### `get_details`

| 파라미터 | 필수 | 설명 |
| --- | --- | --- |
| `ids` | ✅ | 사례 ID 목록. 최대 5건 (M1에서 3건 제한 때문에 관련 사례 6건 중 3건만 열린 사례에서 상향. M5에서 `search`가 최대 10건을 돌려주게 됐지만 상세는 길어 에이전트 맥락을 많이 차지하므로 5건을 유지하고 소개할 사례만 골라 열게 함, 사용자 결정) |

출력: 원문 제목, 회사·발행일, 원문 링크, 필드별(문제 상황, 해결 방법, 성능·운영 포인트, 버린 대안) 요약 전체, **같은 글의 다른 사례 ID**.

- **근거 발췌와 분류·기술·태그를 응답에서 뺀다** (사용자 결정, 2026-10-20, 이슈 #36). 설계 질문 한 번에 sonbae 응답이 세션 컨텍스트의 13~37%를 차지했고, 가장 큰 단위가 `get_details`(1회 약 6.9k 토큰)였으며 그 45%가 근거 발췌였다. 근거를 뺀 이유는 다음과 같다
  - **답변에 거의 쓰이지 않았다**: M7·이슈 #30 실행 기록에서 받은 근거 중 답변에 쓰인 것은 1.5~1.8%이고, 쓰인 경우도 대부분 문장을 옮기지 않고 고쳐 쓴 것이었다
  - **요약을 검증하지 못한다**: 발췌 검증은 발췌가 원문에 있는지만 보고 요약이 발췌와 맞는지는 보지 않는다. 요약에 있는 수치가 함께 붙은 발췌에는 없는 경우도 있었다(case_0311의 60~120fps). 확인이 필요하면 원문 링크로 한다
  - **잃는 정보가 작다**: 근거에만 있고 요약에 없는 의미 있는 수치는 포인트의 약 1~3%(무작위 24개 확인)였고 주로 성능·운영의 개선 전 값이다
  - 지어낸 내용을 거르는 장치는 추출 단계의 발췌 검증이라 응답에 발췌를 싣는지와 무관하다. 발췌는 데이터·배포 DB에 그대로 두고 검증과 색인(원문 표현으로 검색)에 쓴다
  - 근거를 요청할 때만 붙이는 `evidence` 옵션은 두지 않았다 (사용자 결정). 쓰일 일이 드물고 도구 정의만 늘어난다
  - 분류·기술은 에이전트가 `search` 카드에서 이미 봤고, 태그는 색인용 키워드에 가까워 답변에 쓰이지 않는다
- 효과: 평가셋 62개 질의의 상위 5건 응답이 중앙값 9,452자 → 4,285자(−54.7%). 에이전트 평가(M7 과제 32개 × 3회 × 2버전)에서 실행마다 sonbae 결과 글자 수 중앙값이 12,420자 → 9,338자(−25%)이고 `get_details` 호출 수는 그대로였다. 인용 정확도·사례 서술 충실도·답변 품질은 미리 정한 기준을 모두 통과했다 ([M7.md 후속](milestones/M7.md#후속-get_details-응답-줄이기-2026-10-20-이슈-36))

#### `aggregate`

| 파라미터 | 필수 | 설명 |
| --- | --- | --- |
| `group_by` | ✅ | `technology` / `problem_type` / `domain` / `company` / `rejected_alternative` |
| 필터 | | `search`와 같은 필터 |
| `top_n` | | 상위 몇 개. 기본 10 |

출력: 조건에 맞는 전체 항목 수와 회사 수(**모수**), 항목별 건수·회사 수·회사 이름, 항목별 **예시 ID**(바로 `get_details`로 이어가도록). 기술·문제 유형·도메인은 항목마다 여러 개라 해당하는 값마다 세고, 건수의 합이 전체보다 클 수 있다고 결과에 적음.

- 건수 옆에 **수치 있는 성능·운영 포인트 건수**를 함께 표시함 (M3: 사례 N / 인사이트 M 구분을 대신함). **M5 결정** (사용자 결정): 성능·운영 포인트가 있는 항목이 96%(1,263/1,315)라 거의 모든 항목에 붙어 근거가 강한 사례를 구분하지 못했다. 그래서 성능·운영 포인트 문장에 숫자가 있는 항목(690개, 52%)만 센다. 색인 빌드 때 코드(`build_index.has_metrics`)로 판정하므로 재추출이 필요 없다. 카드의 성능·운영 줄은 문장이 있으면 그대로 보여 준다. 숫자가 없는 항목에도 정성적 결과나 운영 경험이 있을 수 있어 결과에 그렇게 적는다
- **기술 집계는 같은 계열을 합쳐 센다** (M5 결정, 사용자 결정): 기술 사전의 `parent`를 반영해 Amazon MSK·Kafka Connect 등을 Kafka 계열로 합치고 '포함'에 하위 기술별 건수를 보여 준다. 한 항목이 계열 안의 제품을 여럿 써도 계열로는 한 번만 센다(Kafka 132건 → 계열 141건). 회사 수도 계열 기준이다
- **기술 필터도 계열로 펼친다** (M6 결정, 사용자 결정): `search`·`aggregate`의 기술 필터에 상위 기술을 주면 하위 기술까지 찾는다("Kafka" → Amazon MSK, Kafka Connect, Kafka Streams, ksqlDB 포함, 132건 → 141건). 하위 기술을 주면 그 기술만 찾는다. 집계의 계열 합산과 필터 결과의 숫자가 같아져 에이전트가 차이를 기억할 필요가 없다. 검색 평가셋 E9(서버 search 그대로, 기술 필터 질문 Kafka·Iceberg 포함)의 지표는 변경 전과 같았다. 조건 표시에는 "Kafka 계열"로 보여 준다
- `rejected_alternative` 기준 집계는 기술 대안이 있는 항목만 대상

```
조건: 문제 유형 = 메시징·비동기 처리 → 98건 (수치 있는 성능·운영 포인트 57) / 8개사
1. Kafka  59건 (수치 있는 성능·운영 포인트 31) · 8개사 (올리브영, 토스, LY, …)  포함: Amazon MSK 11, Kafka Streams 4, Kafka Connect 2, ksqlDB 2  예시: case_1429, case_1428
2. Spring Framework  26건 (수치 있는 성능·운영 포인트 15) · 5개사 (…)  포함: Spring Boot 7, Spring Batch 3, …  예시: case_0494
```

| 인용 전 확인 | `search`·`get_details` 설명에 "답변에 소개할 사례는 모두 get_details로 열어 확인하고, 카드에 없는 내용을 추측으로 채우지 말 것"을 명시. 소개하지 않을 사례까지 열 필요는 없다고 함께 적어 과도한 호출을 막음 (M1에서 열지 않은 글의 내용을 출처처럼 붙이고, 인용한 글과 연 글이 어긋난 사례에서 나온 결정). 이슈 #36부터 상세에는 근거 발췌가 없어 확인 대상은 필드별 요약 전체이고, 결과에 없는 세부는 추측하지 말고 원문 링크를 안내하게 함 |

| 도구 성격 표시 | 세 도구 모두 MCP 도구 annotation으로 읽기 전용(`readOnlyHint`)·비파괴·멱등을 표시. `search`만 검색어를 외부 API(Voyage)로 보내 `openWorldHint`가 참이고(M10), `get_details`·`aggregate`는 외부 통신 없음. 검색 DB를 읽기만 하는 도구의 성격을 클라이언트에 정확히 알림. 클라이언트가 이를 자동 허용에 쓰는지는 클라이언트마다 다름 |
| 검색어 외부 전송 안내 | `search` 설명에 "검색어는 외부 검색 API로 보내므로 사내 코드, 서비스·고객 이름, 비밀 값은 넣지 말고 일반적인 주제로 쓸 것"을 명시. 에이전트가 작업 중인 코드의 고유 이름을 그대로 검색어로 만드는 것을 막음 (이슈 #30, M10부터 검색어를 Voyage로 보냄) |
| 호출 시점 | 동시성, 캐시, 메시징, 장애 대응, LLM 활용처럼 **선택지가 있는 설계를 정할 때**(작업 시작 전뿐 아니라 구현 중에 방식을 고를 때도), 기술을 고르거나 비교할 때, 사용자가 다른 회사 사례를 물을 때, 장애 회고·운영·성능 개선 방향을 정할 때. 단순 CRUD, 버그 수정, 리팩터링, 개념·원리 설명에는 호출하지 않음. 호출 신호와 호출하지 않는 경우는 서버 안내에도 적음 (이슈 #30: Claude Code는 도구 정의를 지연 로드해 처음에는 도구 이름과 서버 안내만 보고 부를지 정함). 서버 안내에는 무엇인지·언제 부르는지·언제 부르지 않는지만 담음 |
| 도구 로드 방식 | 기본 동작(지연 로드)에 맡기고 `search`에 `_meta["anthropic/alwaysLoad"]`를 주지 않음 (사용자 결정, 2026-10-19, 이슈 #30). 호출률 평가에서 기본 동작만으로 경쟁 조건 24/24, 작업 도중 조건 15/18을 불렀고(변경 전 22/24, 9/18), 남은 놓침은 코드를 읽고 바로 구현한 경우라 정의를 미리 보여 줘도 바뀔지 불확실함. 주면 모든 사용자 세션에 `search` 정의 약 2.1k자가 상시 들어감 ([M7.md 후속](milestones/M7.md#후속-호출-판단-개선-2026-10-19-이슈-30)) |
| 인용 규칙 | 결과를 인용할 때 회사명과 원문 링크를 반드시 밝히고, 결과에 없는 사례는 지어내지 않으며, 결과가 없거나 적으면 그렇다고 말함. 도구 설명에 명시. M1에서는 서버 안내와 결과 문구에도 넣었지만, 서버 안내에서는 빼고(호출 판단용, 위 "사례 활용 원칙"), 결과 끝에 붙던 인용·사례 활용 안내는 뺌 (사용자 결정, 2026-10-19, 이슈 #30). 결과가 없거나 적을 때 그 사실과 "지어내지 말 것"을 알리는 문구는 남김 |
| 없는 주제 처리 | 결과가 없거나 적으면 그 사실을 명확히 반환 |

### 배포 로드맵

| 단계 | 코드 배포 | 데이터 전달 |
| --- | --- | --- |
| MVP | git 설치 후 실행 (`uv tool install git+…`, M6 결정) | GitHub Release에서 다운로드 (M6에서 앞당김, 아래) |
| 안정화 + 자동 갱신 | git 설치 유지 (PyPI 전환은 보류, 아래) | 같은 방식 + 최신 DB 하루 1회 자동 확인 (M8) |
| 원격 서버 (M9) | git 설치와 함께 Fly.io 원격 서버(URL 연결, 필요할 때만 켬, 아래 [원격 HTTP 서버](#원격-http-서버-m9)) | 같은 방식 |

- **M6 결정: MVP 설치는 `uv tool install git+…`로 안내한다** (사용자 결정). 처음 계획한 `uvx --from git+…`는 깨끗한 환경 확인에서 약점이 드러났다. uvx는 git 주소를 실행할 때마다 GitHub에서 브랜치의 최신 커밋을 확인(`git fetch`)한다. 그래서 오프라인에서는 서버가 켜지지 않았고(20~30초 뒤 실패), 온라인에서도 initialize가 5.1~6.3초 걸렸다. `uv tool install`은 설치 때 한 번만 받고 실행 때는 GitHub에 접속하지 않아 initialize 2.4~2.6초, 오프라인에서도 정상이었다. 대신 설치·등록이 두 단계가 되고 업데이트는 `uv tool upgrade`로 직접 한다.
- **PyPI 전환은 M8로 넘긴다** (사용자 결정, M8에서 보류로 바뀜. 바로 아래). Python MCP 서버의 일반적인 배포 형태는 PyPI + `uvx <패키지>`다. 이 경우 uvx가 버전 번호로 캐시해 매번 확인하지 않으므로, 한 줄 등록과 빠른 기동을 함께 얻는다. 사용자에게 Git이 필요 없고, 저장소 전체를 checkout하지 않아 Windows 경로 길이 문제도 없다. PyPI 계정과 버전 관리·배포 자동화가 필요해 M6 범위에서 뺐다. 이름 `techblog-mcp`는 2026-10-05 기준 PyPI에서 비어 있다.
- **M8 결정: PyPI 전환은 보류한다** (사용자 결정, 2026-10-13). 원래 PyPI 전환은 데이터 갱신과 엮여 있었다. DB 버전이 코드에 고정돼 있어 새 데이터를 주려면 새 패키지 버전을 내야 했다. M8 4단계에서 서버가 최신 Release DB를 직접 받게 되면서 데이터 갱신에는 PyPI가 필요 없어졌고, 남는 이점은 설치 편의(한 줄 등록, Git 불필요, 빠른 기동)뿐이다. 그런데 M9 원격 HTTP 서버는 URL만으로 연결해 설치 자체를 없애므로 같은 문제를 더 근본적으로 푼다. 원격 서버 배포에도 PyPI는 필요 없다(저장소에서 빌드). 로컬 실행을 원하는 사용자(검색어에 설계 내용이 담겨 외부로 보내고 싶지 않은 경우, 오프라인, 원격 서버 중단 대비)는 지금의 `uv tool install git+…`로 쓸 수 있다. PyPI 계정·버전 관리·배포 워크플로의 관리 부담을 지금 지지 않고, 로컬 사용자가 실제로 생기면 다시 검토한다.
- DB 경로를 불러오는 부분은 `src/sonbae/db.py` 한 곳에 둔다.
- **M6 결정: 검색 DB는 GitHub Release에서 내려받는다** (사용자 결정). git 주소로 설치하면 패키지(`src/sonbae/`)만 설치되고 저장소의 `data/techblog.sqlite`는 따라가지 않는다. 검토한 대안은 세 가지였다.
  - (A) 빌드한 DB를 패키지에 넣기: 가장 단순하지만, 갱신할 때마다 약 9MB 바이너리가 git 기록에 쌓인다.
  - (B) jsonl을 패키지에 넣고 첫 실행 때 빌드하기: 첫 실행이 느리고, 색인 빌드 코드를 서버로 옮겨야 한다.
  - (C) Release에서 내려받기: 원래 안정화 단계에 계획했던 방식이고 M8에 그대로 이어진다. C를 택했다.
- **내려받을 DB는 코드에 고정한다** (사용자 결정). Release 태그·sha256·크기·스키마 버전을 `src/sonbae/db_release.json`에 두고, 받은 파일을 체크섬으로 검증한다. 같은 코드면 항상 같은 데이터를 쓰고, 실행할 때 최신 버전을 확인하는 네트워크 요청이 없다. 데이터를 갱신하려면 `pipeline.release_db --upload`로 새 Release를 만들고 바뀐 `db_release.json`을 커밋한다. **M8에서 바뀜**: 캐시 DB는 최신 Release를 따라가고, 고정 버전은 첫 실행에서 최신 확인이 실패할 때 받는 기준이 된다(아래 [자동 갱신](#자동-갱신-m8)).
- DB는 환경 변수 `SONBAE_DB` → 저장소 `data/techblog.sqlite`(개발용) → 사용자 캐시(Windows `%LOCALAPPDATA%\sonbae`, macOS `~/Library/Caches/sonbae`, 그 외 `$XDG_CACHE_HOME/sonbae`) 순으로 찾는다. 서버는 기동 때 백그라운드에서 DB를 준비해 initialize 응답을 막지 않고, 도구 호출은 준비가 끝날 때까지 기다린다. 다운로드·검증에 실패하면 도구 결과로 이유를 알리고 다음 호출에서 다시 시도한다.

### 자동 갱신 (M8)

`pipeline.update` 한 명령이 새 글만 수집 → 추출 → 문서 확장 → 검색 DB 빌드를 한다. 여러 번 실행해도 결과가 같고(멱등), 실패한 글은 기록을 남기지 않아 다음 실행에서 다시 시도한다.

- **새 글 판단은 추출 기록(`data/posts.jsonl`) 기준** (사용자 결정, 2026-10-11). 추출 기록이 있는 글(제외로 분류된 글 포함)은 원문을 다시 받지 않는다. 원문 캐시(`data/raw/`)는 git에서 제외돼 있어, 캐시 기준이면 캐시가 없는 환경(GitHub Actions 등)에서 1,262편을 모두 다시 받는다. 캐시를 Actions 캐시 등으로 보관하는 안은 원문 전체를 공개 저장소의 실행 환경에 두게 되어 택하지 않았다. 대신 이미 추출한 글이 나중에 수정되어도 자동으로는 반영되지 않는다(필요하면 로컬에서 수집 `--refresh` 후 추출).
- **블로그별 추출 대상 상한, 넘으면 보류** (사용자 결정). 평소 8곳 합쳐 주 10편 안팎인데, 블로그가 URL·ID 체계를 바꾸면 기존 글이 모두 새 글로 보여 중복 항목이 생기고 추출 비용이 든다. 한 블로그의 추출 대상(새 글 + 원문이 바뀐 글)이 상한(기본 30편)을 넘으면 그 블로그는 추출하지 않고 실패로 보고한다. 사람이 확인한 뒤 `--max-new`로 상한을 올려 실행한다.
- **일부 실패는 성공분을 반영하고 실패로 보고** (사용자 결정). 한 블로그 수집이나 한 글 추출이 실패해도 나머지는 반영해 DB를 만들고, 종료 코드로 구분한다(0 정상, 2 일부 실패·보류, 1 실행 불가). 하나라도 실패하면 멈추는 방식은 블로그 하나가 오래 막히면 전체 갱신이 멈춰 택하지 않았다. 알림 방식은 GitHub Actions 단계에서 정한다.
- **발췌 검증 실패분은 별도 파일에 항목 단위로 격리** (사용자 결정, 2026-10-11). `data/quarantine.jsonl`(커밋)에 실패한 포인트(필드·요약·발췌)와 검증 전 항목 전체, 글·모델·프롬프트 버전을 남긴다. 해결 방법이 모두 탈락해 통째로 버린 항목도 여기서 볼 수 있다. 검색 DB에는 넣지 않고, 검증 기준이 너무 엄격한지 LLM이 지어낸 것인지 점검하는 데 쓴다. 글을 다시 추출하면 그 글의 격리분도 바꾼다. 이전 기록은 발췌 문장만 있어(`posts.jsonl`의 `dropped_evidences`, 평가 스크립트가 씀) 그대로 두고 격리는 M8 이후 추출부터 쌓인다.
- **탈락률은 최종과 재시도 전 두 가지로 보고, 표본이 충분할 때 기준값 대비 배수와 절대 하한을 함께 건다** (사용자 결정). 재시도가 첫 시도 탈락을 대부분 메워 주므로(M4 전체 추출에서 31%의 글이 재시도, 최종 탈락률 0.64%) 최종 탈락률만 보면 모델 변경·HTML 구조 변경·프롬프트 회귀를 늦게 안다. 그래서 첫 구조화의 발췌 수·탈락 수를 글별 기록에 추가했다. 이번 실행 발췌가 50개 미만이면 판단하지 않고(주 10편이면 발췌 약 140개라 한두 개로 비율이 크게 흔들림), 이번 탈락률이 하한(최종 3%, 재시도 전 10%) 이상이면서 이전 기록으로 계산한 기준값의 3배 이상이면 급등이다. 재시도 전 기준값은 기록이 쌓이기 전까지 없으므로 하한만 본다. 하한은 M4 최종 탈락률 0.64%와 M3 평가 실행의 재시도 전 탈락률 1.6~3.6%를 보고 정했다.
- **조용한 고장은 목록 크기와 본문 길이로 감지한다** (사용자 결정, 2026-10-14). 블로그가 목록·본문 HTML 형식을 바꾸면 수집기가 오류 없이 빈 결과를 내, 새 글 0편과 구분되지 않고 "정상"으로 끝났다. 두 가지를 본다. ① **목록 크기**: 수집기는 매 실행 목록 전체를 읽고(본문은 새 글만 받음) 추출 기록이 있는 글을 건너뛴다. 이번 목록에서 본 기존 글이 그 블로그 추출 기록의 90% 미만이면 경고한다. 글을 올리지 않은 블로그는 기존 글이 그대로 보이고, 목록 형식이 바뀌면 기존 글도 함께 안 보이므로 둘을 구분할 수 있다. 90%는 블로그가 글 몇 편을 지운 정도는 넘기려는 여유다. ② **본문 길이**: 추출 대상 글의 평문(`html_to_text`)이 300자 미만이면 추출하지 않고 보류한다. 본문 선택자가 관련 글 카드 같은 엉뚱한 요소에 맞으면 오류 없이 짧은 본문이 저장되고, 그대로 추출하면 "제외"로 기록돼 다음 실행에서 다시 받지 않아 영구히 빠진다. 보류하면 기록을 남기지 않고 원문 캐시도 지워 수집기를 고친 뒤 다시 받는다. 기존 1,268편 중 300자 미만은 5편(모두 공지·행사로 제외)이고 추출된 글은 최소 1,201자라, 진짜 짧은 글의 오탐은 1년에 한두 번이다(사람이 `pipeline.extract`로 직접 추출). 둘 다 종료 코드 2로 알린다. **블로그별 공백 기간**(평소 글을 올리던 블로그에서 N주 동안 새 글 없음)은 넣지 않았다. 글을 안 올린 것과 형식 변경을 구분하지 못하고, 실제로 컬리는 수집기가 정상인데 147일째 새 글이 없었다(2026-10-14 확인). 블로그별 탈락률 표시도 넣지 않았다. 블로그 하나의 주간 발췌는 10~30개라 판단 기준을 걸 수 없어 실익이 적다. 남는 사각지대는 기존 글은 목록에 그대로인데 새 글만 다른 사이트맵·URL 형식으로 옮겨 가는 경우로, 메인 페이지·RSS 같은 두 번째 경로와 비교해야 잡을 수 있어 비용 대비 보류했다. 목록을 최신순으로 읽다 아는 글에서 멈춰 요청을 줄이는 안은 목록 크기 검사가 불가능해지고 사이트맵·RSS 블로그는 요청 수도 같아 택하지 않았다.
- **급등해도 배포는 진행하고 알린다** (사용자 결정). 탈락한 내용은 이미 걸러져 DB에는 검증을 통과한 내용만 들어가므로 위험은 오염이 아니라 누락이다. 종료 코드 2로 보고해 워크플로가 알린다. 추출 결과를 되돌리는 방식은 새 글 전체가 늦어지고 되돌리기 로직이 필요해 택하지 않았다.
- **GitHub Actions로 주 1회 실행** (사용자 결정, 2026-10-11). 매주 월요일 09:00(KST)에 실행하고 수동 실행도 가능하다. 8곳 합쳐 주 10편 안팎이라 매일 실행하면 대부분 변경이 없고 블로그 요청만 7배로 는다.
- **데이터 변경은 워크플로가 PR을 만들어 직접 병합한다** (사용자 결정). 데이터가 바뀌면 테스트 → 검색 DB Release 배포 → `db_release.json` 갱신 → `chore/data-update-<실행 번호>` 브랜치 → PR → Merge commit 순서로 사람 개입 없이 반영한다. 저장소 규칙(PR·Merge commit)과 이력을 지키고 추가 토큰이 필요 없다. 기본 토큰(`GITHUB_TOKEN`)으로 만든 PR에서는 CI 워크플로가 돌지 않으므로 같은 린트·테스트를 갱신 워크플로 안에서 돌린다. main에 직접 커밋하는 안은 저장소 규칙에 예외가 생기고, 사람이 병합하는 안은 완료 기준(사람 개입 없이 배포)에 못 미쳐 택하지 않았다.
- **문제는 GitHub 이슈로 알린다** (사용자 결정). 종료 코드가 0이 아니거나 단계가 실패하면 `auto-update` 라벨 이슈에 실행 요약과 실행 기록 링크를 남긴다. 열린 알림 이슈가 있으면 댓글로 이어 붙인다. 부분 실패여도 성공분은 배포한다.
- **서버는 최신 Release를 하루 한 번 확인해 받아 두고 다음 기동부터 쓴다** (사용자 결정, 2026-10-13). M6에서는 같은 코드면 같은 데이터를 쓰고 실행 때 네트워크 요청이 없도록 DB를 코드에 고정했지만, 그러면 매주 배포해도 사용자가 코드를 업데이트해야 새 데이터를 받는다. Release마다 DB와 함께 버전 정보 파일(`db_release.json`)을 올리고 최신 Release로 표시하면, 서버는 `releases/latest/download/db_release.json` 고정 주소로 최신 버전을 알 수 있다. GitHub API가 아닌 다운로드 주소라 비로그인 요청 한도(시간당 60회)를 받지 않는다. 스키마가 서버와 맞고 받아 둔 것과 다르면 백그라운드로 받아 체크섬을 확인한다. 마지막 확인 시각은 캐시 폴더의 `state.json`에 두고 24시간이 지났을 때만 확인한다(MCP 서버는 세션마다 켜지지만 데이터는 주 1회 바뀜). 새 DB는 다음 기동부터 써서 한 세션 안에서 결과가 바뀌지 않고, 열려 있는 파일을 바꾸는 문제(Windows)도 없다. 확인에 실패하면 받아 둔 DB를 그대로 쓰고, 받아 둔 DB가 없으면 고정 버전을 받는다. 받아 둔 버전과 고정 버전 중에는 태그가 새 것을 쓴다(코드를 업데이트하면 고정 버전이 더 새로울 수 있음). 고정 버전만 쓰고 패키지 버전으로 데이터를 갱신하는 안과 환경 변수로 켜는 옵트인 안은, 사용자가 직접 업데이트해야 새 데이터를 받아 택하지 않았다.
- **서버는 도구 호출마다 DB 연결을 열고 닫는다** (사용자 결정, 2026-10-15, [이슈 #22](https://github.com/zie-ning/sonbae/issues/22)). MCP SDK는 동기 도구를 작업 스레드에서 실행해, 에이전트가 도구를 병렬로 부르면 호출이 동시에 돈다. 연결 하나를 나눠 쓰던 때는 질의 결과가 섞이거나 사라져 한쪽이 실패했다. 스레드별 연결도 문제를 풀지만, 여는 비용이 약 1ms라 아끼는 것이 거의 없고 연결 수명이 anyio의 작업 스레드 관리에 달려 테스트에서 DB를 바꿀 때 다른 스레드가 옛 DB를 계속 쓸 수 있어 택하지 않았다. 연결은 기본값(`check_same_thread`)으로 열어 다른 스레드에서 쓰면 바로 오류가 나게 한다.
- **Voyage API 실패가 이어지면 잠시 부르지 않는다** (사용자 결정, 2026-10-18, [이슈 #25](https://github.com/zie-ning/sonbae/issues/25)). 검색이 연속 3번 API 실패(시간 초과, 연결 실패, HTTP 오류 모두)로 대체되면 30초 동안 Voyage를 부르지 않고 바로 단어 일치 검색을 돌려준다. 30초가 지나면 검색 하나로 다시 시험해 성공하면 풀고, 실패하면 다시 30초 막는다. 어차피 대체될 검색이 한도 8초를 다 기다리지 않게 하려는 것이다. 함께 고친 것: 한도를 넘겨 버린 호출은 대기열에서 취소하고, 실행 중인 호출은 httpx 한도를 검색에 남은 시간으로 줘서 일꾼을 오래 붙잡지 않게 한다. 비동기 호출, 사용자별 호출 제한, 결과 캐시는 M9에서 검토한다.
- **Voyage 호출 일꾼을 4개에서 32개로 늘린다** (사용자 결정, 2026-10-19, [이슈 #27](https://github.com/zie-ning/sonbae/issues/27)). 원격 서버에서 잰 결과 동시 검색이 늘면 일꾼 앞 대기열 시간이 지연의 대부분이었고(동시 16개 3.1초), CPU는 검색당 약 16ms였다. 32개로 늘리자 동시 64개가 2.9초에 끝났다. 동기 `search` 도구는 anyio 작업 스레드(기본 40개) 안에서 돌아 일꾼을 40개보다 많이 둘 필요가 없다. 환경 변수 `SONBAE_VOYAGE_WORKERS`로 바꿀 수 있다. 비동기 전환은 보류한다. 처리량 상한은 서버가 아니라 Voyage rerank-3 토큰 한도(등급 1 2M TPM, 검색당 약 21.7k 토큰이라 분당 약 92회)이고, 요청 제한(분당 60회, 몰림 20회) 아래에서는 일꾼 32개로 줄을 서지 않아 비동기로 얻을 것이 없다. Voyage 등급이 올라 한도가 크게 늘고 여러 사용자를 받을 때 다시 검토한다(이슈 #27). 검색당 리랭커 토큰 줄이기는 [이슈 #32](https://github.com/zie-ning/sonbae/issues/32).
- **쓰던 DB 파일이 없어져도 서버가 멈추지 않게 한다** (사용자 결정, 2026-10-15). 연결을 나누면 경로로 파일을 새로 여는 순간이 생기는데, 먼저 기동해 계속 켜져 있는 서버는 받아 둔 최신보다 이전 버전을 쓰고 있어서 다른 서버가 기동하며 정리할 때 그 파일이 지워질 수 있다(연결 하나를 계속 열어 두던 때는 드러나지 않았다). 그래서 새 버전을 받을 때 최근에 받은 3개 버전(`db.KEEP_RECENT_VERSIONS`)은 지우지 않고, 그래도 파일이 없으면(오래 켜 둔 서버, 사용자가 캐시를 비운 경우) 경로를 다시 찾아 그때 쓸 수 있는 DB로 넘어간다. 이 경우에만 한 세션 안에서 DB가 바뀔 수 있다.
- **우아한형제들은 자동 갱신에서 빼고 로컬에서 갱신한다** (사용자 결정, 2026-10-13). 첫 워크플로 실행에서 우아한형제들 WordPress API가 GitHub Actions 서버(데이터센터 IP)의 요청을 403으로 막았다. 로컬 PC에서는 수집된다. 그대로 두면 매주 같은 실패 알림이 반복되므로 워크플로는 `--skip woowahan`으로 실행한다. 우아한형제들 글은 로컬에서 `pipeline.update woowahan` → `pipeline.release_db --upload` → 데이터·`db_release.json` PR로 반영한다. 운영 측에 GitHub Actions 접근 허용을 요청하는 안은 Actions IP 대역이 넓고 자주 바뀌어 보류했고, 사용자 PC를 runner로 쓰는 안(self-hosted runner)은 실행 시각에 PC가 켜져 있어야 하고 공개 저장소에서 보안상 권장되지 않아 택하지 않았다.

### 원격 HTTP 서버 (M9)

- **호스팅은 Fly.io로 한다** (사용자 결정, 2026-10-18). 서버는 형태소 분석기·DB·항목 임베딩을 준비한 상태에서 메모리 약 590MB, 준비 7초가 걸려(로컬 측정) 1GB 머신(shared-cpu-1x)을 쓴다. Fly.io는 켜져 있는 동안만 초 단위로 과금하고(2026-10 공식 가격표 기준 시간당 약 $0.008, 상시 가동하면 월 약 $5.7) 꺼 두면 루트 파일시스템 비용(GB당 월 $0.15)만 낸다. Dockerfile과 `fly.toml`로 배포하고 HTTPS 주소를 기본 제공해, 운영보다 서버 기능(요청 제한·로깅·지연 측정)에 시간을 쓸 수 있다. 검토한 대안은 다음과 같다.
  - AWS EC2: 국내 채용에서 많이 요구해 백엔드 근거로는 유리하지만, OS·TLS·보안 그룹을 직접 관리하고 꺼 둬도 EBS·공인 IPv4 비용이 나간다. 1GB(t4g.micro)는 서버가 겨우 들어가 여유가 없다.
  - Cloud Run: 요청이 없으면 0대로 줄어 비용이 거의 없지만, 깨어날 때 7초 이상 걸리고 상시 1대로 두면 월 약 $45다.
  - Render: 512MB(Starter $7)가 부족해 Standard($25, 2GB)가 필요하다.
  - Hetzner VPS: 같은 값에 자원은 넉넉하지만 운영을 직접 해야 한다. Oracle Always Free: 2026년에 무료 한도가 절반으로 줄었고 인스턴스 확보가 어렵고 회수 위험이 있다.
- **실제 사용자를 받지 않고 필요할 때 켜고 끈다** (사용자 결정, 2026-10-18). 데모·검증용이라 상시 가동하지 않는다. **켜고 끄는 것은 Fly.io 자동 정지·시작에 맡긴다** (사용자 결정, 2026-10-19): 몇 분 동안 요청이 없으면 멈추고, 멈춘 상태에서 요청이 오면 켠다(`auto_stop_machines`, `auto_start_machines`, 최소 0대). 첫 요청은 연결·검색까지 약 15초 걸린다(M9 8단계). 직접만 켜는 안(`auto_start_machines = false`)은 쓰기 전마다 켜야 하고 꺼져 있을 때 연결이 실패해 택하지 않았다. 대신 틀린 토큰 요청도 머신을 깨워 켜진 시간만큼 과금된다(시간당 약 $0.008, 요청이 없으면 다시 멈춤). 첫 요청 지연을 줄이려고 DB를 이미지에 넣는 안은 약 2초만 줄고 새 DB마다 다시 배포해야 해 택하지 않았다(아래). 그래서 M8에서 넘어온 실행 중 DB 교체는 하지 않는다. 자주 재시작하므로 지금의 "하루 한 번 확인해 받아 두고 다음 기동부터 사용"이 그대로 맞는다. 동시 검색이 몰릴 때의 병목([이슈 #25](https://github.com/zie-ning/sonbae/issues/25))도 급하지 않다.
- **원격 서버가 Voyage 키를 보관하고, 토큰 인증을 건다** (사용자 결정, 2026-10-18. M10에서 보류한 키 문제). 키는 Fly.io 시크릿(`VOYAGE_API_KEY`)으로 넣어, 연결하는 쪽은 키 없이 의미 검색을 쓴다. 서버가 켜져 있는 동안 URL은 공개 상태라 남이 내 키로 검색할 수 있으므로, 서버 토큰(Fly.io 시크릿)을 `Authorization: Bearer` 헤더로 확인해 없거나 틀리면 401로 거절한다(토큰은 환경 변수 `SONBAE_TOKEN`). 토큰 없이 로컬이 아닌 주소로 열려고 하면 서버가 기동하지 않아, 설정 실수로 인증 없이 공개되는 일을 막는다(로컬 주소에서는 개발용으로 토큰 없이 실행할 수 있다). 혼자 쓰는 데모 용도라 토큰은 하나로 하고, 사용자별 토큰 발급이나 MCP의 OAuth 인증은 택하지 않았다(사용자를 받을 때 다시 검토). 사용자가 요청 헤더로 자기 Voyage 키를 보내는 안은 키 남용 걱정은 없지만, 키가 없으면 단어 일치 검색만 쓰게 돼 택하지 않았다. 로컬 stdio 서버는 지금처럼 각 사용자의 환경 변수 키를 쓴다.
- **요청 제한은 프로세스 메모리의 분당 한도로 한다** (사용자 결정, 2026-10-18). 토큰 하나로 혼자 쓰므로 사용자별 구분이 필요 없고, 토큰이 새더라도 Voyage 비용이 한없이 늘지 않게 막는 안전장치다. 한도를 넘으면 429로 거절한다. 한 대로 운영하므로 Redis 같은 공유 저장소는 두지 않는다(여러 대로 늘리면 대수만큼 한도가 늘어나는 점은 감수). 토큰 버킷으로 세고 기본 한도는 분당 60회, 몰림 허용 20회다(`SONBAE_RATE_PER_MINUTE`, `SONBAE_RATE_BURST`로 바꿈, 2026-10-18 추천값으로 실험). 최악의 Voyage 비용은 검색당 약 $0.0015 × 분당 60회 = 시간당 약 $5.4로 묶이고, 에이전트가 검색 5개를 병렬로 세 번 부르는 패턴은 모두 통과했다. 매 분 초기화하는 고정 구간은 경계 앞뒤로 한도의 두 배가 통과해 택하지 않았다. 인증 다음에 세어 틀린 토큰 요청은 한도를 쓰지 않는다.
- **여러 대로 늘릴 수 있게 상태 없는 세션과 헬스 체크를 둔다** (사용자 결정, 2026-10-18). 지금은 한 대로 운영하지만 트래픽 대응 설계를 근거로 남긴다. ① Streamable HTTP를 상태 없는 방식(`stateless_http=True`)으로 띄워, 세션이 특정 머신 메모리에 묶이지 않고 어느 머신이든 요청을 받는다(도구가 모두 읽기 전용이라 세션 상태가 필요 없다). ② `GET /health`는 형태소 분석기·DB·항목 임베딩 준비가 끝나면 200, 준비 중이면 503을 돌려준다. Fly.io가 이것으로 준비된 머신에만 요청을 보내고 배포 때 새 머신이 준비된 뒤 옛 머신을 내린다. 플랫폼이 토큰 없이 호출하므로 인증·요청 제한에서 빼고 상태만 담는다(`{"status": "ok"|"starting"|"error", "steps": {"db", "analyzer"}}`). 준비 단계가 실패하면 `error`로 503을 돌려주고, 이유는 경로 등이 담길 수 있어 서버 로그에만 남긴다. 새 DB 버전 확인은 다음 기동부터 쓰므로 준비 완료를 늦추지 않는다. 한 대일 때는 도구 호출이 이미 준비를 기다리므로(`server._resolve_path`) 효과가 작다.
- **로그는 JSON 한 줄씩 표준 출력에 쓰고, 지표 수집은 나중에 한다** (사용자 결정, 2026-10-18). Fly.io가 표준 출력을 수집해 `fly logs`와 대시보드에서 보여 준다. 요청마다 `http_request`(경로·상태 코드·소요 시간), 도구 호출마다 `tool_call`(도구, 소요 시간, 성공 여부, 검색 방식(의미/단어 일치)과 대체 이유, 결과 수, 필터)을 남기고 같은 요청의 로그는 `request_id`(Fly.io의 `Fly-Request-Id`, 없으면 새로 만듦)로 묶는다. **검색어 원문은 남기지 않고 길이만 남긴다**: 사용자의 설계 내용이 담길 수 있어서다. 정상 헬스 체크와 Voyage 호출마다의 httpx 로그는 잡음이라 남기지 않는다. stdio 서버는 표준 출력이 MCP 통로라 이 설정을 쓰지 않고 경고만 표준 오류로 낸다. Prometheus 사용자 지정 지표(`/metrics`를 내부 포트로 열어 Fly.io 관리형 Grafana에서 보기)는 로깅을 먼저 하기로 해 미뤘다.
- **원격 서버는 main에서 자동 배포한다** (사용자 결정, 2026-10-20). 로컬에서 `fly deploy`를 하던 때는 배포본이 어느 커밋인지 사람이 기억해야 했고, 실제로 부하 측정 중 병합 전 브랜치가 배포된 채 남은 적이 있다. `deploy.yml`이 main에 서버 코드가 바뀔 때 CI(`ci.yml`을 재사용)를 거쳐 배포하고, 수동 실행 버튼도 둔다. 데이터만 바뀐 병합은 배포하지 않는다(이미지에 DB가 없고 서버가 기동할 때 최신 DB를 받는다). 배포 뒤 `/health`와 `get_details` 호출로 확인하고(`search`는 Voyage 토큰을 써서 뺌), 실패하면 직전 이미지로 되돌린 뒤 `deploy` 라벨 이슈로 알린다(갱신 워크플로와 같은 방식). 머신은 1대로 유지한다(`--ha=false`, 요청 제한 카운터가 머신마다 따로 있다). 태그를 달 때만 배포하는 안은 혼자 개발하는 저장소에서 절차만 늘고, 수동 실행만 두는 안은 지금의 드리프트 문제를 남겨 택하지 않았다.
- **원격 서버는 포트폴리오용 배포 경험이 목적이고, README에 주소를 노출하지 않는다** (사용자 결정, 2026-10-19). 실제 사용자를 받으려는 배포가 아니라 원격 MCP 서버를 설계·배포·운영해 본 근거(백엔드 직무)를 남기려는 것이다. 사용자용 README는 지금처럼 로컬 설치만 안내하고, 원격 서버의 실행·배포 방법은 [개발.md](개발.md), 설계와 측정은 [M9.md](milestones/M9.md)에 둔다. 문서에도 배포한 앱 주소를 적지 않는다(앱 이름은 `fly.toml`에 있어 주소를 숨기는 것은 아니고, 접근은 토큰으로 막는다).
- **DB는 이미지에 넣지 않고 기동 때 최신 Release를 받는다** (사용자 결정, 2026-10-18). 필요할 때만 켜므로 켤 때마다 최신 데이터를 쓰고, DB가 15MB라 받는 시간이 짧다. 이미지에 넣는 안은 여러 대가 같은 버전을 쓰게 보장하지만 Release마다 다시 배포해야 해 택하지 않았다(여러 대로 운영하게 되면 다시 검토).

### 에이전트 평가 (M7)

- **M7 결정: 세 조건을 비교한다** (사용자 결정, 2026-10-06). 같은 과제를 아래 조건으로 풀게 하고, 시나리오마다 여러 번 실행해 비율로 비교한다.

  | 조건 | techblog MCP | 웹 검색(WebSearch·WebFetch) | 비교하는 것 |
  | --- | --- | --- | --- |
  | `mcp` | 있음 | 차단 | 이 서버를 쓸 때 |
  | `none` | 없음 | 차단 | 모델 기억만으로 답할 때 (기준선) |
  | `web` | 없음 | 허용 | 현실의 대안인 웹 검색으로 사례를 찾을 때 |
  | `web-ask` | 없음 | 허용 + 사례는 웹 검색으로 찾으라는 지시 | 웹 검색을 실제로 쓸 때 (추가, 아래) |

  `mcp`와 `none`의 차이로 서버의 효과를 분리하고, `web`과 비교해 웹 검색 대비 가치를 본다. `web`은 결과가 실행마다 달라 재현성이 낮고, 답변 속 웹 출처의 사실 여부를 따로 확인해야 한다.
- **에이전트 모델은 `sonnet`, 과제마다 조건별 3회** (사용자 결정, 2026-10-06). 호출 금지 과제(`no_call`)는 techblog 도구가 있을 때만 의미가 있어 `mcp` 조건만 돌린다. 과제 28개 기준 234회다.
- **`web-ask` 조건을 추가한다** (사용자 결정, 2026-10-06). `web` 조건 65회에서 에이전트가 웹 검색을 한 번도 쓰지 않았다. 사례를 직접 요청받아도 기억으로 답하고 "원하시면 웹 검색으로 찾아 드리겠다"고 되물었다. 그래서 `web`은 "웹 검색이 있어도 쓰지 않는 기본 행동"으로 그대로 두고, `--append-system-prompt`로 "선택지가 있는 작업에서는 WebSearch로 국내 기업 기술 블로그 사례를 찾고, 회사명·원문 링크를 밝히고, 못 찾은 사례는 만들지 않는다"고 지시한 `web-ask`를 따로 둔다. 지시문은 사용자가 CLAUDE.md에 넣을 만한 수준으로 맞췄다(`eval/agent_run.py`의 `WEB_ASK_PROMPT`). 호출 금지 과제를 뺀 25개 × 3회 = 75회.
- **채점은 답변 품질만 본다** (사용자 결정, 2026-10-06). 처음에는 국내 사례 인용률, 근거 일치, 관련성을 공통 지표로 잡았지만 MCP에 유리하게 기운 설계였다.
  - 사례 인용은 이 서버가 하도록 만든 일 그 자체라, 채점 기준으로 삼으면 "MCP가 MCP 일을 했다"는 것만 확인한다
  - 과제 대부분은 사례를 요청하지 않았고, 사례를 인용하라는 지시는 `mcp` 조건만 도구 설명으로 받았다
  - DB 라벨·사례 ID·원문 링크는 MCP 출력 형식에 맞춘 판정 방식이고, 과제도 DB에 사례가 있는 주제에서 골랐다

  그래서 같은 과제의 두 답변을 나란히 놓고 질문한 개발자에게 어느 쪽이 더 도움이 되는지만 판정한다(`eval/agent_judge.py`). 기준은 정확성·실무 고려·판단 근거·상황 적합성·전달이고, 출처나 사례가 붙어 있다는 사실만으로는 점수를 주지 않는다. 비교 쌍은 `mcp` 대 `none`·`web`·`web-ask`(같은 회차끼리). 채점기에는 조건을 숨기고, 두 순서로 한 번씩 판정해 둘이 같을 때만 승패로 본다(순서 편향 제거). 채점 모델은 다른 계열인 OpenAI `gpt-5.5`(medium). 도구 호출률 등은 결과를 설명하는 진단 지표로만 쓴다.
- **사람 검증은 하지 않는다** (사용자 결정, 2026-10-07). 처음에는 사용자가 21쌍을 조건을 모른 채 판정해 LLM 채점기와 대조하려 했지만, 판정자가 한 명뿐이라 의미가 작다고 보고 뺐다. 결과는 채점기 하나의 판단이며, 순서를 바꾼 두 판정의 일관성(83%)만 신뢰도 근거로 남는다.
- **DB와 무관하게 고른 과제 10개를 더한다** (사용자 결정, 과제 선정은 Claude). DB를 검색하지 않고 흔한 백엔드·AI 설계 질문으로 먼저 쓰고, DB에 사례가 있는지와 상관없이 그대로 실행한다(`open` 분류).
- **전역 `~/.claude/CLAUDE.md`는 그대로 둔다** (사용자 결정). 헤드리스 실행에서 OAuth 로그인을 유지하면서 이 파일만 뺄 방법이 없다(`--bare`는 API 키 필요, `--safe-mode`는 MCP 서버까지 끔). 내용이 응답 언어 규칙뿐이고 세 조건에 똑같이 들어가 비교에는 영향이 없다. 실행 옵션은 [M7 진행 기록](milestones/M7.md#진행-기록)에 있다.

### 조사에서 드러난 사항

- **피드만으로 3년치를 모을 수 있는 곳은 올리브영과 컬리뿐**이다. 나머지는 사이트맵이나 공개 API로 과거 글 목록을 확보해야 한다.
- **수집 방식이 블로그마다 네 가지로 갈린다**: 피드(올리브영, 컬리), 사이트맵 + HTML(우아한형제들, 카카오, 카카오페이, LY), 공개 JSON API(토스, D2), 피드만(Medium 3곳).
- 수집기는 브라우저로 위장하지 않고, 누가 왜 수집하는지 밝히는 User-Agent(예: `TechblogCaseBot/0.1 (+저장소 URL)`)를 사용한다. robots.txt를 지킨다. 봇 확인(Cloudflare 등) 우회는 운영 측 허락을 받은 경우에만 한다 ("수집 예절").
- **Medium 3곳(당근, 무신사, 29CM)은 과거 글을 모을 수 없다** (→ 수집 대상에서 제외하기로 결정). 아카이브 목록은 봇 확인(Cloudflare)으로 막혀 있으며, 당시 원칙에 따라 우회하지 않았다. 피드로 최근 10편씩만 확보할 수 있다.
- **Medium 라이선스 파일(RSL)** 은 AI 입력·색인·검색 용도를 출처 표기 조건으로 허용하고 AI 학습만 금지한다. 이 프로젝트의 용도(추출·색인 + 원문 링크)는 허용 범위에 가깝지만, 같은 사이트의 robots.txt는 AI 크롤러를 전면 차단하고 있어 입장이 일관되지 않는다.
- 카카오는 Nuxt 기반이라 본문이 HTML이 아닌 스크립트 데이터에 들어 있어 블로그 전용 파서가 필요하다. 토스는 Next.js지만 글 페이지에 본문이 서버 렌더링돼 있다 (M2에서 확인).
- **우아한형제들은 수집기의 요청을 WAF가 차단한다** (M2에서 확인). 차단 페이지는 "올바른 접근 요청이 아니어서 접근할 수 없다"는 안내이고, User-Agent가 같아도 curl은 통과하므로 클라이언트 지문으로 거르는 것으로 보인다. 운영 측 허락을 받은 뒤(2026-09-30) 이 호스트만 시스템 curl로 요청해 수집했다. User-Agent·robots.txt·요청 간격은 그대로 적용한다.
- 각 블로그의 이용약관은 M6에서 확인했다 (위 "저작권과 이용약관").

- 사례 소개 방식 개선 (M7 결과): 도구 설명과 `/sonbae` prompt가 사례를 출처와 함께 따로 소개하게 해, 답변이 사례에 분량을 쓰면서 설계 내용이 줄었다. 사례는 설계 판단을 바꿀 때만 짧게 녹여 쓰게 고치고 `mcp` 조건만 다시 평가할지, 언제 할지 미정 ([M7 결과](milestones/M7.md#결과)). DB에 없는 주제에서 비슷한 카드를 사례처럼 소개하는 문제(M7 t22, 무관 인용 9건)도 같은 갈래로 함께 본다
